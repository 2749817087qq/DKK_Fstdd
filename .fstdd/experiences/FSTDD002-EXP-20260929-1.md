## 现象

节点执行上游升级流程：`git fetch server master` 后 `git merge --ff-only server/master`。实测发现 `server/master` 领先本地 7 个提交（含 `stdd_version` 升到 3.1.0、guard 作用域修复等），本地又领先 origin 110 个提交（含一条本地 gate 修复 `30af397`）。执行 `git merge-base --is-ancestor server/master HEAD` 返回退出码 1 —— 即本地并非 server 的祖先，ff-only 不可行。

最小复现：
```
git fetch server master
git merge-base --is-ancestor server/master HEAD && echo FF_OK || echo NO_FF   # -> NO_FF (exit 1)
git rev-list --count HEAD..server/master   # -> 7
git rev-list --count origin/master..HEAD   # -> 110
```

## 为什么危险

- **静默**：若升级脚本在 ff-only 失败后默认 fallback 到 `git reset --hard server/master`（或 `git merge --no-ff` 强行合入），过程不会报错，但会**单向、不可逆地丢弃本地独立提交**（如 `30af397` gate 修复）。
- **单向恶化**：本地修复一旦被 reset 覆盖，无备份 tag 即永久丢失；若在无人值守的定时自动化中发生，发现时早已错过恢复窗口。
- **影响面**：节点基线整体回退到 server 态，本地适配（guard / install / gate 修复）全部作废，后续任务建立在错误基线上。

## 更一般的形态

任何“拉取式升级 / 同步”（git ff-only、`rsync --delete`、配置下发覆盖）在**分叉**时都存在同样陷阱：默认合入策略在分叉点二选一会丢失某一侧。正确抽象是——**合入前必须先判“可快进性”，分叉 = 冻结 + 上报，绝不自动破坏性同步**；破坏性动作（reset --hard / 强推 / --delete）一律需人工批准。

## 判据（修复后如何证伪）

升级流程新增前置闸门：
1. `git fetch server master` 后，先跑 `git merge-base --is-ancestor server/master HEAD`；退出码 0 才允许 `git merge --ff-only`；
2. 退出码非 0 → 打保命 tag `backup-before-<主题>-<时间戳>`，**停手**并回执说明，请求 K / D哥 裁定（--no-ff 保留本地 fix / 或 pin 回某基线）；
3. 任何 `reset --hard` / `push --force` 必须有显式人工批准，脚本不得内置该 fallback。
