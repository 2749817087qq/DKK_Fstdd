# 症状

凭据轮换后：
- 替换脚本报告「N 个文件、每个替换 1 处，全部成功」，文件 md5 也都变了；
- 但某个服务仍报 **认证失败**：
  `asyncpg.exceptions.InvalidPasswordError: password authentication failed for user "..."`；
- 或者一直没报错，直到某天某个消费者被重启 —— 才发现它拿到的是**已失效的旧凭据**。

# 为什么危险

1. **静默漏改**：替换计数与 md5 都「看着正常」，没有任何报错。
2. **旧凭据仍有效**：漏改的字段继续持有旧口令 ⇒ **轮换的目的（销毁已泄露凭据）未达成**。
3. **可能被永久掩盖**：若目标消费者还有一个**更早的失败点**（如 import 期依赖崩溃），
   它永远走不到「用凭据连库」这一步，缺陷就**不会显形** —— 本例正是如此，被掩盖了一段时日。

# 正确做法

1. **先查优先级**：读应用取凭据的那段代码，确认是「独立键优先」还是「DSN 优先」。
2. **替换模式覆盖全部形态**：
   - DSN：`postgresql://<id>:<pwd>@`
   - 方言 DSN：`postgresql\+[a-z0-9_]+://<id>:<pwd>@`
   - 独立键：`^PG_PASSWORD=.*$` / `^PGUSER=.*$` / `<X>_TOKEN=.*$` ……
3. **逐键比对作为收尾硬判据**：对每个文件里**每一处**凭据取哈希，与旧/新值比对，
   **断言「旧值残留 == 0」**，非 0 必须逐条列出（禁抽样、禁只看计数）。
4. **修复后重跑全部验收判据**：不要假定「修完就好」。本例正是「修好第一层（bcrypt）才看见第二层（凭据键）」。
