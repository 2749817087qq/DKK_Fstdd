## 背景

本 change 的端到端验证必须**故意制造一次镜像失败**（把 github remote 指向不可达地址），
验证告警链路后恢复。这是本 change 唯一触碰生产服务器的动作，风险评分最高（5）。

## 反例（若不这样设计会发生什么）

| 天真做法 | 后果 |
|---|---|
| 日志/标记写生产路径 | 生产 `mirror.log` 被验证噪声污染；假故障写入真实故障标记，**污染后续巡检结果** |
| `git remote set-url` 改真实配置 | 中途异常 → 服务器 remote 指向不可达地址 → **镜像永久失效** |
| 恢复依赖 GitHub 可达 | GitHub 走代理时段性 502（本项目已知现象）→ 恢复失败 → 留在故障态 |
| 恢复后不验证 | 命令报了「成功」，但实际没改回去，无人发现 |

## 本 change 的实际设计（已实测）

| 手段 | 实现 |
|---|---|
| 日志/标记隔离 | `FSTDD_MIRROR_LOG` / `FSTDD_MIRROR_FLAG` → `/tmp/fstdd-e2e/`（实测生产日志零污染） |
| 目标注入 | `FSTDD_MIRROR_URL` —— **直传**给 `git push` / `git ls-remote`
作为目标参数，**不改配置**（初版用 `GIT_CONFIG_KEY_0=remote.github.url`，
实测无效，见 EXP-20260917-A4） |
| 故障态目标 | `http://127.0.0.1:9/nope.git`（快速失败，不依赖外网） |
| 恢复态目标 | 服务器上临时裸库（本地路径，push 必成功） |
| 异常安全 | `trap cleanup EXIT INT TERM` + 恢复后读回验证（实测输出 `[OK] 现场已还原`） |

实测结果：**PASS=38 / FAIL=0**，连续两次运行结果一致。

> ⚠️ 该数字后来被推翻。那次「全绿」掩盖了注入机制无效（`GIT_CONFIG_*` 不生效），
> 使镜像三态判定实际上**从未被真正验证**。改用直传目标后，E2E 才第一次真的
> 测到三态，并立刻暴露出四条断言全红。
> **教训：验证脚本自己「绿」不等于验证有效。** 见 EXP-20260917-A4。

## 实测补充（第二次踩到同一类问题）

本 change 的**变异测试**最初也直接改 `tools/*.sh` 原件再还原，同样在进程被 kill 时留下残留：

```
tools/deploy_server_bare_repo.sh:270  MIRROR_TARGET="${FSTDD_MIRROR_URL:-origin}"   <- 应为 github
tools/check_mirror.sh:98              export GIT_CONFIG_COUNT=1                     <- 多余一行
```

改为**纯内存变异**（静态变异在内存文本上做，行为变异把变异后的源码写入临时目录
执行）后，零文件改动、单进程秒级完成。

**要点：`trap` / `finally` 只在「进程有机会执行清理」时有效。**
被 SIGKILL、容器被杀、断电时都无效 —— 而验证脚本恰恰最常在这些场景下中断。
所以「异常安全」的更强形式不是「加 trap」，而是**从设计上不需要清理**。

## 一般化

**验证脚本的验收标准不是「能发现问题」，而是「无论中途怎么中断，环境都能回到原状」。**
但除此之外还有一条同样重要的：**验证脚本必须真的构造出目标场景** ——
若注入机制没生效，脚本会「绿」着跑完，而它本该验证的分支一次都没被执行到。
把「恢复」当异常安全（trap + 读回验证）而非普通步骤处理；
把「故障注入目标」选成**本地可控**的，而不是真实的外部依赖 ——
否则「制造故障」与「恢复现场」两件事会互相干扰。
