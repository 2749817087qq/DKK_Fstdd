## 现象

change `2026-09-29-clean-rename-residue` Part C 中，skill 步骤要求用
`fstdd experience list --format json` 加载匹配经验。实测该命令在**本仓当前经验库**上直接抛栈：

```
File ".../python3.13/json/encoder.py", line 180, in default
    raise TypeError(f'Object of type {o.__class__.__name__} ...')
TypeError: Object of type date is not JSON serializable
```

崩溃点在渲染分支，而不是取数分支 —— 也就是说 `--format json` 这个契约在本库上从未成立过。

## 根因

经验记录的 `first_seen` / `last_seen` 在 YAML 里是**裸日期**（部分带引号、部分不带）。
`yaml.safe_load` 把不带引号的那个解析成 `datetime.date`，随后
`json.dumps(...)` 没有 `default=`，默认编码器遇到 `date` 就抛 `TypeError`。

## 为什么它一直没被发现

同一份数据的**人读分支**（表格 / YAML 输出）会调用 `str()`，所以从不报错；
只有机器消费的 `--format json` 分支会崩。测试若在内存里手造字符串样本，
就绕过了 YAML 解析这一环，缺陷被完美跳过 —— 属于「用假数据测真接口」的空白区。

## 处置

- 本仓库不修 `upstream/`（vendored，SC-NS-009）；消费侧改用 `--format yaml` / 直接读
  `.experience-index.yaml`，并在 test-plan 里把这条记为上游交棒项。
- **不要在文档/脚本里写 `--format json` 当作可用契约**，除非在同库上真跑过一次。

## 一般化

**机器消费格式（JSON）必须在真实数据上验证一次**，而不是在人造样本上。
日期、Decimal、Path 这类「YAML 会自动转型」的值，是 JSON 输出的固定崩溃点。


## 同库第二处复现（C4 补记，2026-09-30）

同一缺陷在**另一条代码路径**上再次实测到，故记于此（同一 change 内的第二条路径，
不计作第 2 次独立命中，`occurrences` 保持 1）：

```
$ fstdd experience list --format json
TypeError: Object of type date is not JSON serializable
  upstream/fstdd/cli/commands/experience.py:468  print(json.dumps(experiences, ensure_ascii=False, indent=2))
```

`first_seen` / `last_seen` 这类裸日期字段被 YAML 解析成 `datetime.date`，`list` 与
`stats` 分支同样缺 `default=`。**推论**：上游凡 `json.dumps(<从 YAML 读来的对象>)` 处皆同病，
消费侧一律改用 `--format yaml` 或直接读索引文件。
