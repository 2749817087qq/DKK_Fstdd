## 现象

按 README 装完 7 个全局 skill，命令行输出全部 `[OK]`，校验脚本也 `[PASS]`，
但之后在对话里无论怎么触发都不生效 —— 像是根本没装。

## 根因

WorkBuddy 的 skill 装载目录是**环境变量派生**的，不是写死的：

| 环节 | 取值 |
|---|---|
| Electron 主进程 `configureElectronApp()` | 把环境变量 `CODEBUDDY_CONFIG_DIR` 设为配置根目录（该值来自 `WORKBUDDY_CONFIG_DIR`） |
| CLI 的 `getHomeDir()` | 读环境变量 `CODEBUDDY_CONFIG_DIR`，缺省回退到用户主目录下的 `.codebuddy` |
| CLI 的 `getHomeSkillsDir()` | 把 `getHomeDir()` 的结果拼接 `skills` |
| CLI 的 `loadSkills()` | 把 `getHomeSkillsDir()` 作为 `"user"` 源扫描 |

安装器硬编码的 `~/.workbuddy/skills` 是**兜底值**，只在环境变量未设时才等于真实目录。
本机 `WORKBUDDY_CONFIG_DIR` 指向另一个目录，于是「安装成功」与「实际加载」落在两个地方。

更隐蔽的是：仓库内部对这一点的记载自相矛盾 —— shell 包装脚本的注释写对了，
python 实现写错了，而包装脚本调 python 时从未导出覆盖变量，所以错的那层静默胜出。
两处都「看起来对」，只有把两层都读一遍才能发现。

## 处理

1. 安装器与校验脚本改为按 `WORKBUDDY_CONFIG_DIR` → `CODEBUDDY_CONFIG_DIR` → `~/.workbuddy`
   的顺序解析 `skills` 子目录，`FSTDD_OUT` 仍可覆盖但默认走解析。
2. 校验脚本不再复制一份解析逻辑，直接 import 安装脚本里的函数，
   消除两份拷贝漂移的可能。
3. shell 包装脚本显式解析同一份判定并导出 `FSTDD_OUT`，让两层不可能分歧。
4. 把已装到错误目录的 skill 移到备份目录，重装到正确目录。

## 性质

这是**跨平台/多形态产品的路径推断错误**，不是实现缺陷。

教训：当「安装目标」由宿主的环境变量决定时，**任何硬编码默认值都是一个未经验证的假设**；
而且这类错误**不会报错** —— 安装与校验全绿，失败只体现在「装了没用」上。
判定装载目录时不要靠读内核源码推断（本案例的作者就是这么推断错的：看到内核里
某个目录名出现 0 次，就断定它不加载那里，忽略了变量注入这条路径），
应当直接比对运行时的实际 skill 列表与候选目录是否 1:1 全等。
