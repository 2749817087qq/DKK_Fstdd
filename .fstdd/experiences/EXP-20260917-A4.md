root_cause: |
  `remote.<name>.url` 是 git 的**多值**键：第一个值用于 fetch，**全部**值用于 push。
  环境变量注入（`GIT_CONFIG_COUNT` / `GIT_CONFIG_KEY_n` / `GIT_CONFIG_VALUE_n`，
  等价于 `git -c key=value`）只是往这个列表**末尾追加**一项，而**不是替换**。

  于是产生一种极难察觉的失效：
    · `git config --get remote.github.url` -> 返回**注入值**（看起来成功了）
    · `git remote -v` -> 注入值被标成**额外的 push URL**
    · `git ls-remote github` -> 依旧走**第一个** URL（真实远端）

  「查询接口」与「实际行为」给出相反的答案，而人只会去查前者。
detection_trigger: "用环境变量或 `-c` 覆盖 remote 的 URL；或注入后只验证 `config --get` 就认为生效"
fix_template: |
  1) **把目标作为命令的普通参数传入**，不要试图覆盖 remote 配置：
     `git ls-remote "$TARGET"` / `git push "$TARGET" --all`
     （`$TARGET` 可以是 remote 名，也可以是任意 URL / 本地路径），
     完全绕过 remote 配置解析
  2) 保留默认值语义：`TARGET="${FSTDD_MIRROR_URL:-github}"` —— 生产不设该变量，
     行为与改造前完全一致
  3) **验证注入是否生效，必须看端状态而不是配置查询**：
     `git ls-remote` 的实际输出 / `git remote -v` 的目标列表；
     绝不能用 `git config --get`（它会骗你）
  4) 刻意构造一次**必然失败**的场景来证伪（如指向 discard 端口 `127.0.0.1:9`）——
     若「不可达」没有导致失败，说明注入根本没生效

## 背景

镜像失败告警 change 的端到端验证需要把镜像目标从生产 GitHub 切到临时库
（既能制造失败，又不碰真实配置）。为此给钩子与巡检命令加了 `FSTDD_MIRROR_URL`，
初版实现方式是 `GIT_CONFIG_*` 环境变量覆盖 `remote.github.url`。

## 反例（实测证据）

服务器 git 2.43.0，注入 `http://127.0.0.1:9/nope.git`（端口 9 = discard，连接必被拒）：

```
$ git -C <bare> remote -v
github  git@github.com:2749817087qq/DKK_Fstdd.git (fetch)
github  git@github.com:2749817087qq/DKK_Fstdd.git (push)
github  /nonexistent/repo.git                     (push)   <-- 注入值成了额外 push URL

$ GIT_CONFIG_KEY_0=remote.github.url GIT_CONFIG_VALUE_0=/nonexistent/repo.git \
    git -C <bare> config --get remote.github.url
/nonexistent/repo.git                                      <-- 查询：像是生效了

$ 同上环境 git -C <bare> ls-remote github refs/heads/master
c11789a8ea7da33bb7dbfc6761c114a439622a90                  <-- 行为：仍连真实远端
```

## 造成的实际后果

| 后果 | 说明 |
|---|---|
| 判定分支测不出来 | 巡检的「无法测量 / 滞后」依赖「目标不可达」「sha 不一致」两个场景；注入无效使两者都无法构造 —— E2E 四条断言全红 |
| 「零污染」声明不成立 | 真实 GitHub 仍留在 push 目标里，验证脚本**真的推了线上**（所幸内容一致，推送为 no-op，未造成数据污染） |
| 单元测试全程未发现 | 单测用 stub ssh 回放端状态，**绕过了注入路径** —— 绿得毫无意义 |

## 一般化

**「看起来生效」比「明显不工作」更危险。** 明显不工作时人会去查；看起来生效时人会直接相信。

凡是靠**覆盖配置**实现的注入，都要用**实际行为**（而非配置查询接口）验证一次，
并刻意构造一个**必然失败**的场景 —— 如果失败没有发生，就说明注入没生效。

值得警惕的同类形态（「查询接口」与「实际行为」不一致）：

- `git config --get` 与 git 实际解析结果
- 环境变量覆盖与程序内部默认值
- 代理设置与真实出口 IP
- 配置项「已设置」与「已生效」
