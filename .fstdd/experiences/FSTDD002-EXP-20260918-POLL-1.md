## 现象

把轮询标准件挂进 Windows 任务计划程序后，任务状态显示「成功运行」，
但业务输出为「远端文件 0 个」，日志中另有：
`UnicodeDecodeError: 'gbk' codec can't decode byte 0x8d in position 92`
（抛在 `threading._readerthread`）。同一脚本在 Git Bash 交互会话里跑完全正常
（「远端文件 16 个」）。

## 根因

标准件用 `subprocess.run(..., capture_output=True, text=True)` 读 ssh 输出。
`text=True` 未指定 `encoding` 时，Python 按 **locale 默认编码**解码；
Windows 任务计划环境的 locale 是 GBK（cp936），而 ssh 输出的远端中文文件名是 UTF-8 字节。
GBK 遇到 `0x8d` 这类字节直接抛 UnicodeDecodeError，异常发生在 subprocess 的读取线程内，
主流程只拿到空字符串 → 误判「远端 0 个文件」，且**退出码仍为 0**，属静默错误而非失败。
交互式 Git Bash 会话的 `LANG`/`PYTHONIOENCODING` 通常已是 UTF-8，因此掩盖了该缺陷。

## 检测触发

- 症状：调度器报「成功」，业务输出却是 0/空（不是非零退出）；
- 关键判据：日志出现 `_readerthread` 的 UnicodeDecodeError；
- 交叉验证：同一命令交互 shell 正常、调度器异常 → 定为环境差异，不要误改代码。

## 修复模板

在调度器 wrapper 中注入 UTF-8 运行环境（**不改标准件代码**）：

1. `PYTHONUTF8=1` —— Python UTF-8 模式，一并影响子进程输出读取编码；
2. `PYTHONIOENCODING=utf-8`；
3. `LANG=C.UTF-8` / `LC_ALL=C.UTF-8` —— 影响 ssh 自身输出；
4. 调度器 PATH 需显式前置 ssh/scp 所在目录（Git 自带 OpenSSH 不在系统 PATH）；
5. `HOME`/`USERPROFILE` 需显式设置——ssh 靠它定位 `~/.ssh/config` 与 known_hosts；
6. 标准件不带 `-i` 参数时，用 `~/.ssh/config` 的 Host 段统一指定 IdentityFile，
   避免改脚本。

## 复现

调度器下不设 `PYTHONUTF8` 执行 → 「远端文件 0 个」+ UnicodeDecodeError；
设置后重跑 → 输出正确条数。

## 证据

- 修复前日志：UnicodeDecodeError 'gbk' 0x8d + 「远端文件 0 个」；
- 修复后日志：「远端文件 16 个 | 未处理任务 0 个」（由任务计划实际触发产生）；
- 相关配置：ssh Host 段 IdentityFile + wrapper 五项环境变量，均在回执中列明。
