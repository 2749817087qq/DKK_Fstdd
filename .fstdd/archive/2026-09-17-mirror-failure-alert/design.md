# 镜像失败告警：让 GitHub 镜像失效不再无声 - 技术设计

## Context

### 现状

上一轮 change（`2026-09-17-server-bare-repo-mirror`）已落地 L1 数据面：服务器裸库为唯一真值源，
经 `post-receive` 钩子**非强制**镜像到 GitHub。

| 层 | 组件 | 状态 |
|---|---|---|
| L1 数据面 | 服务器裸库（唯一真值源） | ✅ 已落地并验证（三方 sha 收敛） |
| L1 镜像通道 | post-receive → GitHub（Deploy Key） | ✅ 已打通（端到端实测约 6s） |
| L1 镜像**告警** | —— | ❌ **本变更要补的缺口** |

### 本变更的出处（上一轮 design 已明确列为后续项）

`2026-09-17-server-bare-repo-mirror/design.md` 的风险表原文：

> | 非强制推送导致 GitHub 分叉时镜像长期失败而不自知 | 失败写入 `mirror.log`；
> **需纳入运维巡检项（后续 change 可加告警）** |

本变更即兑现该后续项。

### 实测事实（本变更的出发点）

```
钩子输出        { ... } >> "$LOG" 2>&1        ← 全部落盘，推送方看不到
钩子退出码      exit 0                        ← 恒成功，推送方无法从退出码感知失败
失败分支        echo "[WARN] ..."             ← 仅一行文本，无其他动作
mirror.log      21 行 / 2 次镜像 / WARN 0 次   ← 告警路径从未被真实触发过
fstdd timer     systemctl list-timers | grep fstdd → 空；crontab 仅一条无关任务
控制面节点      curl /nodes → {"nodes": []}   ← 无任何已注册节点
控制面契约      POST /messages 要求 from_node_id 已注册；MESSAGE_KINDS 含 notice
文档            DISTRIBUTED_ACCESS.md:84 「查镜像日志」= 人工 ssh + tail
```

**关键判断**：正因为"失败才写 WARN"、而实测 WARN 为 0，说明**这条告警路径至今从未被验证过** ——
它的有效性是一个未经检验的假设。

### 约束

- 架构硬规则：**GitHub 不可达不阻塞任何流转** → 告警不得改变 push 的成败
- 上一轮 design 决策：**非强制推送** → 不得引入 `--force`
- 服务器是公网机器；钩子运行在纯 bash 环境，**不引入额外依赖**
- 远端命令在本 agent 环境存在**执行两次**的特性 → 部署动作必须幂等
- 控制面（8788）为单机自建服务 → 告警**不得强依赖**它
- 宪法：Gate 确认必须人工；`.fstdd.yaml` 的阶段字段只能由受控 CLI 写入

## Decisions

### 1. 四层告警通道，而不是单一通道

**方案**：镜像结果同时投向四个互相独立的出口 ——

| # | 出口 | 面向谁 | 时效 |
|---|---|---|---|
| ① | `tee` 回显到推送方 stdout | **当次推送的人/agent** | 即时 |
| ② | `mirror.log`（保持落盘） | 事后追溯 | 持久 |
| ③ | `mirror-failed.flag` | **自动化程序** | 状态化 |
| ④ | `POST /messages`（notice） | **协作层其他节点** | 异步 |

**为什么**：四种接收方的需求互不替代。

- 推送方需要**即时**知道 —— 否则他会以为推成功了（这正是本变更要消除的"无声"）
- 事后追溯需要**日志** —— 但日志是给"已经知道要去看的人"的
- 自动化流程需要**可程序读取的状态** —— 解析日志文本做判断是脆弱的
- 其他 agent 需要**进入消息流** —— 它们不会去 tail 别人的服务器日志

**备选方案及排除原因**：

- 备选 A：**只做回显（tee）** —— 成本最低，但"过去发生过的失败"不留任何可查询痕迹；
  一个 agent 推送后离线，故障就对所有人不可见
- 备选 B：**只做控制面消息** —— 推送方仍然无感（违背 REQ-001），且告警强依赖控制面可用性
  （违背 SC-012）
- 备选 C：**只做服务器定时巡检（systemd timer）** —— 引入最长一个巡检周期的滞后窗口；
  且需要额外的状态去重与"钩子是否执行过"的判断；实测服务器当前**无任何 fstdd timer**，
  新增一个常驻服务只为这件事，运维面扩张不划算
- 备选 D：**失败时让钩子返回非零退出码** —— 见 Decision 5，会造成语义矛盾

### 2. 故障标记用独立文件，而不是写进数据库或日志字段

**方案**：镜像失败写 `/home/ubuntu/fstdd-git/mirror-failed.flag`（键值行），
镜像全部成功时 `rm -f` 清除。

**为什么**：

- **最小依赖**：纯文件，不依赖控制面、不依赖日志解析、不依赖任何外部服务
- **语义简单**：存在即故障、不存在即正常；清除就是删除
- **可被任何工具读取**：`cat` / `grep` / Python / 巡检脚本都能消费
- 钩子运行在 shell 中，写文件是最自然的动作，不引入新依赖

**备选方案及排除原因**：

- 备选 A：**写进控制面 SQLite** —— 引入控制面依赖（违背 SC-012：控制面不可达时告警仍须生效）
- 备选 B：**在 mirror.log 里加结构化字段** —— 读取方仍需解析日志（违背 SC-007）
- 备选 C：**用钩子退出码表达** —— 违背 SC-013（钩子必须 `exit 0`）
- 备选 D：**在裸库内写 ref 或 tag 作标记** —— 会污染真值源的内容，且会被镜像到 GitHub，
  把"运维状态"混进"代码内容"，语义污染严重

### 3. 控制面告警复用既有 `/messages` 接口 + 注册基础设施节点身份

**方案**：在控制面注册一个**与 agent 节点区分**的基础设施节点身份，钩子以该身份调用既有的
`POST /messages`（`kind=notice`）投递告警。

**为什么**：

- `POST /messages` **已具备所需全部能力**：`notice` 已在 `MESSAGE_KINDS` 中，
  契约无需任何扩展
- **零控制面代码改动** → 控制面正在服务中，改它意味着重新部署与回归，风险与收益不成比例
- **基础设施节点语义成立**：服务器确实承载 L1 数据面与 L2 控制面，它是这个分布式系统里的
  一个真实节点，而不是冒充某个 agent
- 同时解决了 `from_node_id` 必须已注册这一硬约束（实测 `nodes` 表为空）

**备选方案及排除原因**：

- 备选 A：**给控制面新增 `POST /alerts` 端点** —— 需要改 hub 代码、重新部署、重跑控制面测试；
  且会把"告警"与"协作消息"割裂成两套机制，而它们本质是同一件事
- 备选 B：**复用某个 agent 节点的身份** —— 语义错误：告警不是那个 agent 发出的，
  会让消息流中的来源失真
- 备选 C：**不接控制面，只保留 ①②③ 三层** —— 可行但丢失"其他节点可见"这一层；
  在 6 agent 协作场景下，这正是"告警"相对"日志"的核心增量

### 4. 控制面上报是尽力而为，不得成为新的单点

**方案**：上报带短超时，失败即放弃（`|| true` 兜底），仅追加一行本地日志。

**为什么**：

- 控制面是**单机自建服务**。若告警强依赖它，则"控制面故障"会同时摧毁告警能力 ——
  用一个单点去解决另一个单点的可见性问题，是负收益
- 四层出口**互相独立**：控制面不可达时，①②③ 完全不受影响（SC-012）
- 镜像钩子运行在推送的关键路径上（推送方在等它返回），**任何额外的阻塞都是对推送体验的伤害**

**备选方案及排除原因**：

- 备选 A：**上报失败则重试直到成功** —— 会在控制面故障时把钩子拖住，
  直接违反"不阻塞流转"的硬规则
- 备选 B：**上报失败则本地排队、下次推送补发** —— 引入状态机与持久队列，
  对一个"告知性"需求而言过重

### 5. 告警不走退出码 —— 钩子必须保持 `exit 0`

**方案**：镜像失败时，钩子仍以 `exit 0` 结束；告警只通过输出与标记表达。

**为什么**：

- **真值源（裸库）已经更新**。从数据面语义看，这次 push 是**成功的** ——
  镜像只是对外通道的同步，不是推送的成败条件
- 架构硬规则明写「GitHub 不可达不阻塞任何流转」
- 若钩子返回非零，`git push` 会向使用者报失败，**但数据其实已经落库**。
  这会制造"报失败但其实成功了"的混乱 —— 使用者会倾向于重推，甚至被诱导去强推，
  风险远大于"静默"

**备选方案及排除原因**：

- 备选 A：**失败时 `exit 1`** —— 语义矛盾（数据已落库却报失败）；
  且会诱导使用者用 `--force` 重推，与"非强制推送"的既有决策正面冲突
- 备选 B：**失败时阻塞等待人工确认** —— 直接违反"不阻塞流转"，且钩子无交互能力

### 6. 文档同步与能力同批交付，而不是「以后补文档」

**方案**：`docs/DISTRIBUTED_ACCESS.md` 的改写属于本变更的**交付条件**，与钩子、标记、巡检命令**同批**落地。

**为什么**：

- 现有文档**主动教人**用「人工 `ssh` + `tail` 日志」判断镜像状态（第 84 行），
  并把 `[WARN]` 的人工处置写成流程（第 113 行）。若能力升级而文档不动，
  文档就会**教人做已经被取代的事** —— 按本项目既有规矩，这比没有文档更糟
- 6 个 agent 分布在 3 台机器上，他们**不会读钩子源码**；文档是这条能力的唯一发现入口
- 巡检命令若不出现在文档里，就等于不存在（呼应 REQ-009：能力必须能被别人拿到并用起来）

**备选方案及排除原因**：

- 备选 A：**本变更只改代码，文档另开 change** —— 会留下一个「文档与实现互相矛盾」的窗口期，
  而窗口期正是最容易误操作的时候（人工 tail 后判断为正常、实际已滞后）
- 备选 B：**只加一句「已支持告警」** —— 不给出命令与处置路径，使用者仍要读源码才知道怎么用

## Architecture

```
   开发机（FSTDD001…006，3 台机器）
        │  git push server
        ▼
  ┌──────────────────────────────────────────────────────┐
  │ 云服务器 43.134.236.80                                │
  │                                                       │
  │  /home/ubuntu/fstdd-git/stdd-repo.git                 │
  │  （L1 数据面 · 唯一真值源）                             │
  │        │                                              │
  │        │ post-receive（同步执行 · 非强制 · exit 0）     │
  │        ▼                                              │
  │   ┌──────────────────────────────────────┐           │
  │   │  镜像尝试                              │           │
  │   │    git push github --all               │           │
  │   │    git push github --tags              │           │
  │   └──────┬──────────────────────┬─────────┘           │
  │          │ 全部成功               │ 任一失败            │
  │          ▼                       ▼                    │
  │    rm -f mirror-failed.flag   写 mirror-failed.flag    │
  │          │                    + 结构化告警块            │
  │          └───────────┬────────────┘                   │
  │                      ▼                                │
  │        四个互相独立的告警出口                           │
  │   ┌──────────────────────────────────────────┐        │
  │   │ ① tee → 推送方 stdout      （即时）        │        │
  │   │ ② mirror.log               （落盘）        │        │
  │   │ ③ mirror-failed.flag       （状态）        │        │
  │   │ ④ POST /messages notice    （尽力而为）    │        │
  │   └────────────────────┬─────────────────────┘        │
  │                        │                              │
  │  127.0.0.1:8788  L2 控制面（SQLite）                   │
  │     nodes: 基础设施节点（新注册）                        │
  │     messages: kind=notice                              │
  └──────────────────────────────────────────────────────┘
        │
        │ 镜像
        ▼
  GitHub 2749817087qq/DKK_Fstdd（镜像 / 对外通道）

  本地侧（开发者 / agent）：
    tools/check_mirror.sh   ← 一条命令：裸库 sha vs GitHub sha + flag 状态 + 明确退出码
```

**数据流**：agent 本地提交 → `git push server` → 落裸库 → 钩子同步镜像 →
成功则清标记，失败则四路告警 → 推送返回（无论镜像成败，退出码均为 0）。

**故障域**：

| 故障 | 影响范围 |
|---|---|
| GitHub 不可达 | 镜像失败并告警；裸库与各机流转**不受影响** |
| 控制面不可达 | 告警降级为 ①②③；推送与镜像**不受影响** |
| 钩子本身崩溃 | 推送仍成功（`exit 0` 兜底）；镜像缺失由巡检命令的 sha 比对发现 |

## Risks / Trade-offs

| 风险 | 缓解措施 |
|------|----------|
| 标记文件与真实状态不一致（如人工删了标记、或修好镜像后无人推送） | 巡检命令**以 sha 比对为准**，标记只作辅助信息；两者都呈现，不互相替代 |
| 每次失败都发控制面消息，可能产生重复噪音 | 使用 `idempotency_key`（由失败项 + 时间窗口派生）去重；同一故障窗口只投递一次 |
| 钩子逻辑变复杂，可能出现 bash 级缺陷 | 保持纯 bash、无外部依赖；`bash -n` 语法校验；用真实失败场景端到端验证（而非只做静态检查） |
| 基础设施节点身份被误用于其他用途 | 命名与 `capabilities` 明确标注其角色；文档中写明它仅用于系统级事件 |
| 模拟镜像失败时可能把服务器留在故障态 | agent spec 的 preconditions 已写明"模拟后必须恢复现场"；验证步骤含恢复与标记清除检查 |
| 回显内容可能干扰 `git push` 的机器解析 | 告警块置于镜像日志区段内，不影响 git 自身的协议输出；巡检命令不解析 push 输出，只比对端状态 |
| 新增的巡检命令本身可能失效（如 SSH 别名未配） | 巡检命令的退出码区分"不收敛"与"无法检查"，避免把工具故障误判为镜像故障 |
| 巡检命令在 Windows 侧创建后**丢失可执行位**，其他节点执行报 `Permission denied`；或依赖了 `jq` 等非必需工具 | 提交时显式恢复 mode 755；依赖限于 `bash` + `git`；由 TC-MFA-024 断言可执行位与最小依赖（经验库 `EXP-20260915-B4` 的复发形态） |
