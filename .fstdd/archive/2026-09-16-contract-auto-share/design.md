# 契约面一致性 + Phase 4 静默回传 - 技术设计

## Context

### 当前系统状态（实测）

**契约面三处，均为 AI 当指令读的文本，且都存在陈旧内容：**

| 文件 | 行 | 现状 |
|---|---|---|
| `FSTDD_CONSTITUTION.md` | 35 | 「Phase 4 (Deliver) 自动上传经验到**社区** + 同步知识图谱」（上游残留） |
| `upstream/fstdd/cli/commands/init.py` | 254-259 | 「经验数据不外发」+「需要回传时**显式执行**」（措辞与既定语义相反） |
| `upstream/fstdd/cli/commands/upgrade.py` | 285 等 | UPGRADE_NOTES 的 rules 含「Phase 4 DELIVER 自动同步知识图谱」+ 4 处旧名 |
| `.fstdd/onboarding/AI_OPERATING_MANUAL.yaml` | 113 | `stdd archive（自动合并 specs + 上传经验 + 同步知识图谱）` |

**`upgrade.py` 那份会在 SessionStart 注入给 AI**（源码注释：`for AI self-learning on SessionStart`），
其中 `rules` 被当**现行规则**读，故危险程度与宪法同级。

**本仓库根宪法陈旧的原因**：`init.py` 中 `if const_path.exists(): return`（不覆盖已存在文件），
它**永远不会被重新生成**；`.fstdd/memory/FSTDD_CONSTITUTION.md` 更是直接缺失。

### deliver skill 的三级链路（关键发现）

```
upstream/.fstdd/skills/deliver.md                 ← 上游真源，153 行，含 Step 2.8
        │
        │  tools/install_workbuddy_skills.py :: apply_deliver_policy()
        ▼
~/.workbuddy/skills/fstdd-deliver/SKILL.md        ← AI 实际读到的，188 行
```

`apply_deliver_policy()` **已经**在做「锚定 `DELIVER_ANCHOR` → 注入策略块 → 锚点失效则兜底前置 →
写入哨兵 `FSTDD_LOCAL_POLICY_NO_UPLOAD_V1`」这件事。**这是本功能的天然挂载点。**

**但现状是矛盾指令并存**（实测安装位置）：

```
第  89 行  ### Step 2.8: 经验自动上传（V2.9.6）
第  91 行  > ⛔ [本机安装策略：默认禁用]<!-- FSTDD_LOCAL_POLICY_NO_UPLOAD_V1 --> ... 一律跳过 ...
第  94 行  在完成归档和规范合并后，自动将本次 change 中沉淀的经验上传到社区 git 库。   ← 上游原文仍在
第  98 行  2. 逐条上传：python bin/stdd experience share <EXP-ID>
第 156 行  ✅ 经验上传: <N 条上传成功 / 无新增经验 / ⚠️ M 条失败>
```

策略块只**前置一句注释**，**没有移除**上游正文。AI 读到的是「跳过」与「自动上传到社区」两句冲突指令。

### 约束

- **不改动接收端点**（`inbox_server.py`）与脱敏规则——复用既有 `sanitize()` 与 `publish()`。
- **不新增回传实现**：`tools/share_experience.py` 已具备双通道 + 分批 + 退避重试，直接复用。
- 托管 python 3.13.12 未装 pytest，测试须用 `C:/Python311/python.exe`。
- 全量测试基线 **424 passed**，不得回归。
- 另有 active change `inbox-review-sync`（消费侧），本变更**不得**与其范围重叠。

## Decisions

### 1. 静默回传的实现位置：改造 `apply_deliver_policy`，而非新写步骤

**方案**：把 `SECURITY_NOTE_DELIVER` / `SECURITY_BLOCK_DELIVER` 从「默认禁用 + 让用户手动 share」
改写为「**静默回传到我方指定位置**」策略块；并**用替换而非前置**的方式处理 Step 2.8 正文。

**为什么**：该函数已经在做锚定/注入/兜底/哨兵四件事，是同一关注点的既有设施。
另起一套会产生**两个真源**，日后必然漂移——而"契约漂移"正是本变更要修的病。

**备选方案及排除原因**：
- 备选 A：直接在 `upstream/.fstdd/skills/deliver.md` 里改 Step 2.8 文本 → 排除。该文件是上游真源，
  改它等于把上游文本与我们的策略混在一起，上游升级即被覆盖，且丢失「上游原文 + 本机策略」的边界。
- 备选 B：在 `platforms/*/skills/fstdd-deliver.md` 里改 → 排除。实测该目录不是安装器的输出
  （安装器写 `~/.workbuddy/skills/<name>/SKILL.md`），改它对使用者无效。

### 2. 必须**替换**上游正文，不能只前置一条注释

**方案**：锚点命中时，把「锚点之后直到下一个同级标题」的整段上游正文替换为静默回传策略块。

**为什么**：实测现状是矛盾指令并存。AI 面对冲突指令的行为不可预期——
保留上游「自动上传到社区」的正文，等于给 AI 留了一条**指向第三方**的语义入口，
而这正是 REQ-002 要锁死的东西。仅靠"注释优先"是不可靠的约定。

**备选方案及排除原因**：
- 备选 A：保留正文，只把注释写得更强（如全大写、加 ⛔）→ 排除。仍是靠优先级约定，
  且 SC-005 要求「不存在指向第三方的可执行路径」，留着正文会让静态扫描产生歧义。
- 备选 B：整文件替换 deliver skill → 排除。会丢失上游对 Phase 4 的其余步骤。

### 3. 零阻塞：包一层「永不抛出」的调用

**方案**：静默回传调用点用显式超时 + 全异常捕获；失败只写审计与摘要，
**不改变 DELIVER 的退出码**。

**为什么**：回传是**附加价值**，不是交付的必要条件。使用者可能身处无网环境、
端点可能被封、GitHub 可能不通（我们自己的网络就时段性 502）。任何情况下都不该让
"经验没传上去"变成"变更没交付"。

**备选方案及排除原因**：
- 备选 A：回传失败即报错退出 → 排除。会把可选动作变成硬依赖，违背零阻塞要求（SC-007）。
- 备选 B：后台异步不等待 → 排除。进程可能已结束导致请求被丢弃，且无法写审计记录。

### 4. 可审计：项目内 append-only 的 `.fstdd/share-audit.yaml`

**方案**：每次回传追加一条记录（时间 / 经验 id / 目标 / 结果 / 原因），文件加入 `.gitignore` 不入库。

**为什么**：静默意味着使用者不看过程，但**必须能事后查**——这既是透明性，也是我们排障的唯一线索
（本次 429 问题就是靠"服务器实际落了 30 个文件"才发现链路其实是通的）。
不入库是因为它属本机运行态，且含本机路径。

**备选方案及排除原因**：
- 备选 A：写系统临时目录 → 排除。会被清理，不可查（SC-009 明确要求项目内可预期路径）。
- 备选 B：入库随项目提交 → 排除。属运行态数据，且会把使用者环境信息带进仓库。

### 5. 可关闭：环境变量优先，配置文件持久

**方案**：`FSTDD_NO_SHARE=1` 立即生效（不发起任何请求）；
`.fstdd/config.d/experience.yaml` 增加 `share.silent.enabled`（默认 true）作为持久开关。

**为什么**：环境变量适合"这次先别传"的临时场景与自动化环境；配置文件适合长期选择。
两者都读、环境变量优先，是 CLI 工具的通行做法。

**备选方案及排除原因**：
- 备选 A：只做配置文件 → 排除。自动化/CI 场景不便临时关闭。
- 备选 B：只做环境变量 → 排除。使用者每次都要设置，等于没有持久选择。

### 6. 目标锁死：复用既有常量，不新增目标定义

**方案**：静默回传只调用 `tools/share_experience.py`，其目标来自既有 `DEFAULT_EXP_REPO`
与 `inbox_url()`；不引入任何新的目标常量或 URL 字面量。

**为什么**：目标越多，锁死越难。单一来源 + 静态扫描断言（SC-005）是最容易守住的组合。

**注意（易误判点）**：`upstream/.fstdd/config.d/experience.yaml` 的 `community.registries`
**确实**指向 `leonai42/stdd-experiences`——但那是**拉取（只进）**源，属既定策略
（可拉上游社区，不外发我们的数据）。静态扫描必须区分**拉取**与**外发**，
否则会误报（我们已有同类教训：脱敏正则误伤 `README.md`）。

### 7. 契约面单一真源 + 漂移守护

**方案**：`init.py` 的宪法模板为**唯一真源**；本仓库根副本改为**由模板生成**（不再手工维护）；
新增测试断言「仓库副本 == 模板输出」逐字节一致。

**为什么**：本次漂移的根因就是"副本与模板各改各的"。让副本变成产物，漂移在结构上不可能发生；
再加逐字节断言，改坏了立刻红。

**备选方案及排除原因**：
- 备选 A：只手工修副本，不加测试 → 排除。下次改模板时必然再次漂移（本次就是复发）。
- 备选 B：让 init 每次覆盖已有宪法 → 排除。会摧毁使用者自定义（且现有 `exists() → return` 是有意为之）。

### 8. 存量升级：片段级迁移，不做整文件覆盖

**方案**：在 `upgrade.py` 新增 `_migrate_constitution()`，与既有 `_migrate_dirs_to_stdd()` 并列调用；
流程为「先备份（复用 `_backup_project_files`）→ 只替换已知陈旧片段 → 报告改动清单」；
迁移后内容与目标一致则不再改动（幂等）。

**为什么**：`init.py` 的 `exists() → return` 有意保护使用者自定义，所以**不能**用"整文件重新生成"
来修存量项目——那会把使用者的自定义条目一起抹掉。片段级迁移是唯一既能修正、
又能保留自定义的做法。

**备选方案及排除原因**：
- 备选 A：整文件覆盖（先备份）→ 排除。备份不等于不丢失：使用者不会去 diff 备份。
- 备选 B：不迁移，只提示用户手工改 → 排除。D哥 明确要求纳入范围；
  且"提示了但没人做"等于漂移长期存在。

### 9. 顺带修复 `validate` 的 TC-ID 误判（阻塞 Gate 2 的工具缺陷）

**方案**：`validate.py` 的 TC-ID 提取从「全文正则计数」改为「只统计案例定义行」
（形如 `| **ID** | TC-XXX-001 |`）。

**为什么**：test-plan 模板本身含「测试执行矩阵」与「建议补充顺序」两节，
在其中**引用**已有 TC-ID 是模板规定的正常写法；按全文计数会把引用误判为「重复的 TC-ID」，
**使模板规定的格式反而无法通过校验**——即工具与既定契约矛盾。
该检查的真实意图是「两个案例不得共用同一 ID」，故应只统计案例定义行。

**发现方式**：本 change 的 test-plan 严格按模板编写后，`fstdd validate` 报 16 个「重复 TC-ID」，
全部来自矩阵与优先级列表的引用。归档样例
（`2026-09-15-crlf-eol-governance/test-plan.md`，TC-EOL-001 出现 3 次）同样如此，
说明是工具缺陷而非写法问题。归档 change 未被 validate 覆盖，所以一直没暴露。

**反向验证**：修正后注入真实重复（同一 `**ID**` 行出现两次）仍被捕获 → 检查未被削弱。

**备选方案及排除原因**：
- 备选 A：改我的 test-plan，去掉 ID 引用 → 排除。等于迁就工具缺陷，下一个人会再撞一次；
  且模板与工具的矛盾仍在，属于本次要修的同类问题。

### 10. 契约面扫描的「可执行 vs 说明」判定规则

**方案**：静态扫描（SC-005）按「是否构成可执行路径」判定，而非简单字符串匹配：
出现于**赋值/调用/URL 字面量** → 判为可执行；出现于**注释、文档、历史说明、拉取配置** → 判为说明。

**为什么**：仓库中**确实存在**合法引用，简单匹配必然误报：
- `tools/inbox_server.py`、`experience.py` 的注释里写着「两条外发通道均已永久移除」（历史说明）
- `upstream/.fstdd/config.d/experience.yaml` 的 `community.registries` 指向
  `leonai42/stdd-experiences`——但那是**拉取（只进）**源，属既定策略

我们已有同类教训（脱敏正则误伤 `README.md`、`design.md`），故此处必须显式区分，
否则要么误报、要么为了"扫干净"而删掉合法说明。

**备选方案及排除原因**：
- 备选 A：简单 grep 计数为 0 → 排除。必然误报（实测已有说明性引用），
  且会导致有人去删掉那些说明，反而丢失"已移除"的证据。
- 备选 B：只扫 `tools/` → 排除。覆盖不全，`upstream/` 与 `skills/` 同样会被 AI 读到。

## Architecture

```
【契约面：单一真源 + 生成产物 + 漂移守护】

  init.py 宪法模板 ──生成──> FSTDD_CONSTITUTION.md（仓库根）
        │                    └─ .fstdd/memory/FSTDD_CONSTITUTION.md
        │
        └── 测试断言：仓库副本 == 模板输出（逐字节）

  upgrade.py 迁移 ──片段级修正──> 存量项目的旧宪法（先备份，保留自定义）


【静默回传：真源 → 策略注入 → 安装产物 → 复用回传】

  upstream/.fstdd/skills/deliver.md            （上游真源，不改）
        │
        │  apply_deliver_policy()  ★改造点
        │   · 锚定 Step 2.8 → 整段替换为「静默回传」策略块
        │   · 锚点失效 → 兜底前置（保留既有行为）
        │   · 注入哨兵 FSTDD_LOCAL_POLICY_NO_UPLOAD_V1（保留，verify 依赖）
        ▼
  ~/.workbuddy/skills/fstdd-deliver/SKILL.md   （AI 实际读到的）
        │
        │  Phase 4 (Deliver) 触发，静默执行、无交互
        ▼
  tools/share_experience.py --export --publish （复用，零新实现）
        │
        ├─ 有凭证 → Fstdd-experiences（直推；无写权限自动 fork + PR）
        └─ 无凭证 → 自建端点 43.134.236.80:8787（待审核池）
        │
        ▼
  .fstdd/share-audit.yaml                      （审计记录，append-only，不入库）


【关闭开关】

  FSTDD_NO_SHARE=1（环境变量，优先） ─┐
                                     ├─> 跳过回传，不发起任何请求，摘要明示
  experience.yaml: share.silent.enabled=false ─┘
```

## Risks / Trade-offs

| 风险 | 缓解措施 |
|------|----------|
| 静默回传被指「偷偷外发」，损害信任 | README 明示机制与目标；提供关闭开关；审计记录可查；契约面写清「静默回传到我方指定位置、不向第三方外发」 |
| 无人工逐条把关 → 凭证/PII 泄漏 | 双防线：客户端**强制**脱敏（不可绕过）+ 服务端二次校验（命中即拒、不落盘）；TC-CAS-012/013 双向断言 |
| **语义机密无法自动识别**（脱敏兜不住） | 明确不承诺"绝对安全"；把关点放在我方审核池（入库前人工审核）；文档写明边界 |
| 零阻塞实现不当，反而变成阻塞 | 显式超时 + 全异常吞掉 + 退出码不受影响；TC-CAS-008 断言退出码、TC-CAS-009 断言耗时上限 |
| 改造 `apply_deliver_policy` 破坏既有 verify 哨兵 | 保留 `SENTINEL` 常量与 grep 语义；同步更新 `verify_workbuddy_skills.py` 的判定；写后校验保留 |
| 锚点随上游改版失效 | 保留既有兜底路径（锚点失效→前置策略块）+ `[WARN]` 输出；TC-CAS-004 断言安装产物含静默回传步骤 |
| 存量升级误删使用者自定义条目 | 片段级替换（不做整文件覆盖）+ 升级前备份 + 幂等断言（TC-CAS-019）+ 报告改动清单 |
| 静态扫描误伤说明性/拉取性引用 | 扫描必须区分「可执行 vs 说明」「拉取 vs 外发」；`experience.yaml` 的 registries 为拉取源，显式标注（TC-CAS-006 备注） |
| 契约面断言空转（"检查了但永远通过"） | 变异验证必做：注入 4 个缺陷，要求**全部**被捕获（TC-CAS-021） |
