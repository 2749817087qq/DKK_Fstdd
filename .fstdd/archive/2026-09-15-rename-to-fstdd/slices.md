# Fstdd 改名切片执行计划

## Dependency Graph Summary

```
[独立命名空间]  ← 零依赖节点（唯一 capability）
      │
      ├── S1 标识层 ────────────┐
      │      (TC-001/002)       │
      │                         ▼
      ├── S2 CLI 与包 ──────── 顺序依赖（S1 完成后）
      │      (TC-003/004)       │
      │                         ▼
      └── S3 数据目录 ──────── 顺序依赖（S2 完成后）
             (TC-005/006)
```

**并行化说明**：
- **无并行组**。三个切片存在**严格顺序依赖**：
  - S2 的 CLI 名依赖 S1 确定的 skill 名（二者需一致）
  - S3 的数据目录依赖 S2 的包结构（CLI 读目录的逻辑在包内）
- 依赖图显示 `zero_dependency: ["独立命名空间"]`，这是 **capability 层面**无依赖；
  切片层面因改动对象耦合而必须串行。

## Rationale

### Slice S1: 标识层（P0，先行）

- **依赖关系**：无前置。是 S2 的基础——CLI 名与 skill 名必须一致，先定标识。
- **风险分析**：经验库匹配 **EXP-A4（正则误伤，high）** 与 **EXP-A6（照单执行，high）**。
  替换规则的自匹配是上次失败的直接原因，本切片以「单次扫描」算法规避。
- **新增测试**：2 个断言脚本（TC-001 无 FFSTDD 自匹配 / TC-002 无旧标识残留）

### Slice S2: CLI 与包（P0，依赖 S1）

- **依赖关系**：依赖 S1 —— skill 里引用的 CLI 路径必须与 S1 确定的命名一致。
- **风险分析**：Python 包改名会导致 import 断裂，失败形态是「CLI 完全不可用」，
  比 S1 的文本误伤更严重。缓解：改完立即跑 `fstdd --help` + init/new/status 冒烟。
- **新增测试**：2 个端到端（TC-003 CLI 冒烟 / TC-004 隔离安装）

### Slice S3: 数据目录（P0，依赖 S2）

- **依赖关系**：依赖 S2 —— 数据目录的读取逻辑位于 Python 包内，包未改名则目录改名的验证无意义。
- **风险分析**：**本次最高风险**。`.fstdd/` 下有 2 个已归档 change（不可再生资产），
  1939 处代码引用依赖该目录名。失败形态是**数据丢失**，不可逆。
  缓解：迁移前 bundle 备份；迁移后双重验证（status + 目录内容）。
- **新增测试**：2 个（TC-005 历史资产可访问 / TC-006 三项校验）

## 降级预案

| 触发条件 | 动作 |
|---|---|
| 某切片连续 3 次修复失败 | 降级为普通模式，暂停报告 |
| 三项校验通过率 < 95% | 暂停，人工判断 |
| S3 迁移后历史 change 不可读 | **立即回滚**（bundle 恢复），暂停报告 |
| 发现数据丢失风险 | 立即停止，不继续 |
