# FSTDD 节点交付物入库规程

> 适用版本：FSTDD 3.0.x+
> 最后更新：2026-09-25
> 来源：2026-09-25《节点交付物价值评估》—— 发现"沉淀率低"问题

## 一、问题（实测）

评估 7 个节点的交付物后发现：**代码类进了主仓，文档类大半没进**。

| 交付物 | 体量 | 当时状态 |
|---|---|---|
| 002 `fstdd_selfcheck.py`（跨平台自检脚本） | 7.0 KB | ❌ **仅在 notices/，不在主仓** |
| 003 《per-node 接入 SOP》 | 9.6 KB | ❌ 同上 |
| 005 《日志采集与噪音治理》 | 9.2 KB | ❌ 同上 |
| 006 《协议差距评估》 | 14.1 KB | ❌ 同上 |
| 006 《macOS 兼容报告》 | 9.0 KB | ❌ 同上 |

⇒ **"交了就沉底"**：躺在 `notices/` 目录里，**不进版本、不可检索、新节点天然看不到**。

## 二、规程（强制）

### 2.1 判定：什么算"实质交付"
凡满足以下**任一**，即为实质交付，**必须入主仓**：
1. **可执行物**：脚本、补丁、测试、配置；
2. **可复用文档**：SOP、规程、操作手册、模板；
3. **可引用报告**：评估、审计、兼容性、根因分析（≥ 3 KB 且含结论）。

**不算实质交付**：纯"收到/确认"类回执、状态说明、进度同步。

### 2.2 入仓位置

| 类型 | 位置 |
|---|---|
| 脚本 / 补丁 | `tools/` |
| 测试 | `upstream/tests/` |
| 规程 / SOP | `.fstdd/standards/` |
| 报告 / 评估 | `docs/` |

### 2.3 入仓格式（**保可追溯**）

每个入仓件**必须附来源头**：

- Markdown：
  ```
  <!-- ARCHIVED-BY-K provenance
  source_node: FSTDD0NN
  original_path: notices/FSTDD0NN/<原文件名>
  archived_at: YYYY-MM-DD
  note: 由 K-main 按《节点交付物入库规程》收进主仓
  -->
  ```
- 脚本：文件头注释同义（`# ARCHIVED-BY-K provenance: source_node=... | original=... | archived_at=...`）

### 2.4 入仓前置校验

| # | 检查 | 要求 |
|---|---|---|
| 1 | 语法 / 可运行性（脚本类） | `python -m py_compile` 通过 |
| 2 | 无凭证明文 | 全件扫描 64-hex / token 关键词 |
| 3 | 来源可追溯 | 来源头齐全 |

### 2.5 责任
- **节点**：交付即声明"是否实质交付"及建议入仓位置；
- **K**：按本规程**在收到后入仓**（不等迭代末），并在回执中确认"已入仓 + commit"；
- **未入仓的实质交付视为未交付**（避免"交了但没人用得上"）。

## 三、与回执量的关系

**回执量 ≠ 价值**（实测：回执量最大的节点曾出空壳交付）。
⇒ 判价值**看是否入仓 / 可执行 / 被采纳**，不看件数。
