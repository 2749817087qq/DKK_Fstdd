# FSTDD003 收 · Phase 1 执行方式增补（**任务卡驱动**）

## 一、为什么改（**这是给你的减负，不是加活**）

实测（口径申报 5/6 已回）：**六节点里只有 002 实现了 seed 排程器**；其余节点明确回"未实现 / 不确定"，
003 明确"不自判休息日、以任务卡驱动"。

⇒ 规范 `plan/13 §1.1` 假定的"每节点自算休息日 + 自开窗口"**在多数节点上不具备实现条件**。
⇒ **K 侧增补一条路径：由 K 按你的人设时段，逐窗口下发任务卡；你只执行。**

## 二、你的新工作方式（**只这一条变化**）

| 项 | 原 | **新** |
|---|---|---|
| 今天做不做 | 你按 seed 自算"是否休息日" | **看 K 是否给你发了窗口卡**（发卡=做，不发=不做） |
| 做多少 | 你自算窗口数/动作数 | **窗口卡上写明**（本窗口建议 N 个动作） |
| 何时交回执 | 你自定窗口 | **窗口结束 +15 分钟内**交 `<NODE>复-phase1-<日期>-<HH>.md` |
| **其他** | — | **全部不变**（白名单 / 硬上限按日 / 红线 / 判据） |

**⇒ 你不需要写任何排程代码、不需要实现 seed 算法。** 收到卡就做，做完回执即可。

## 三、硬上限仍按「日」计（**别超**）

窗口卡只给"本窗口建议动作数"；**当日总量仍不得超你任务卡里的日配额**
（001=15 / 002=15 / 003=15 / 004=10 / 005=15 / 006=14）。

## 四、若你**已经**实现了 seed 排程器（如 002）

**可以继续用你自己的排程**，但**以 K 的窗口卡为准**（卡到即做；卡未到但你自算该做，也可做，
回执照常交）。⇒ **两种方式并存不冲突**，判据不变。

## 五、本通知的生效
- **即刻生效**；首个窗口卡随后下发；
- 若你**收不到**卡（怀疑漏发）⇒ 回执 `FSTDD003复-未收到窗口卡.md`（写日期/窗口/你的活跃时段），
  **不要**自行按 seed 开窗口（避免与统一节奏错位）。

—— **K**（判定以服务器时钟为准）
