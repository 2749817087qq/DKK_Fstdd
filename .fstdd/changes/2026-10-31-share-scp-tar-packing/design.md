# 经验回传 scp 通道改 tar 打包 - 技术设计

## Context

### 现状：5 步流程，第 4 步是瓶颈

`tools/share_experience.py:_scp_dir()`（88 行）当前流程：

| 步 | 动作 | 命令 |
|---|---|---|
| 0 | 白名单校验（防命令注入） | `_validate_remote_path()` × 3 |
| 1 | SSH 可达性 | `ssh -o ConnectTimeout=5 alias echo OK` |
| 2 | 远端目录可写 | `ssh alias "mkdir -p ... && touch probe && rm probe"` |
| 3 | 建批次目录 | `ssh alias "mkdir -p {remote}/{node}-experiences-{ts}"` |
| **4** | **scp 全部文件** | **`scp -r -- <112 个文件路径> host:dir/`** |
| 5 | 验证远端文件数 | `ssh alias "ls {batch}/*.md \| wc -l"` |

第 4 步显式枚举文件（不用 `dir/*` glob）是为了绕开「Windows scp 不展开通配符」的坑
—— 但代价是 **112 个源文件全塞进一条命令行**，实测耗时 **5m19s**。

### 为什么慢：不是带宽，是往返次数

112 个文件 = 112 次独立的 SFTP 传输协商。每次几毫秒到几十毫秒，累计起来就是分钟级。
**打包成 1 个文件 ⇒ 1 次协商**，这是数量级的差异，不是百分比优化。

### 后果：假失败比慢更严重

外层 timeout 一到就 SIGTERM ⇒ `returncode≠0` ⇒ 判失败 ⇒ 降级 inbox（本机无 token）⇒ 401
⇒ 审计记 failure。**但已传的文件留在服务器上。**

实测三次超时留下 13 / 25 / 37 个文件的半成品批次，审计全记「失败」——
这个假信号直接导致 2026-10-30 误报「112 条待传」。

### 环境事实（已实测）

| 项 | 值 |
|---|---|
| 远端 tar | `/usr/bin/tar`，**GNU tar 1.35**（Ubuntu 22.04） |
| 本机 Python | 3.13.12，`tarfile` 标准库可用 |
| 典型文件数 | 89 → 112（随经验库增长） |
| 单文件大小 | 1-5 KB |

## Decisions

### 1. 用 Python `tarfile` 而非系统 `tar` 命令

**方案**：`import tarfile`，在临时目录生成 `.tar.gz`。

**为什么**：
- **跨平台一致**：Windows 的 `tar.exe`（bsdtar）与 GNU tar 在 `--exclude` / 权限位 /
  长路径处理上有差异；Python 标准库行为在所有平台一致。
- **不依赖 PATH**：系统 tar 可能不在 PATH（尤其 Windows 精简环境）。
- **可控的 arcname**：见决策 2 —— 只有 Python API 能逐条指定 `arcname`。

**备选方案及排除原因**：
- 备选 A：`subprocess.run(["tar", "-czf", ...])` → 排除。跨平台行为不一致，且要处理
  Windows 路径分隔符与 GNU/BSD 参数差异。
- 备选 B：`zipfile` → 排除。压缩率低于 gzip，且远端解包要 `unzip`（不是所有发行版预装）。

### 2. `arcname=os.path.basename(f)` 强制扁平化

**方案**：打包时每个成员只保留文件名，剥掉所有目录成分。

**为什么**：
- 从根上消除路径穿越 —— tar 成员名不可能含 `../`，远端解包时物理上无法写到批次目录外。
- 现有 `_scp_dir` 的 `-` 开头文件名拒绝校验继续生效（打包前跑）。

**备选方案及排除原因**：
- 备选 A：保留相对路径 + 远端解包时校验成员名 → 排除。校验代码多、易漏（tar 支持
  `--absolute-names` / 符号链接等绕过手法）；扁平化是**结构性免疫**，不是「检查后放行」。
- 备选 B：不打包，改用 `rsync` → 排除。Windows 无原生 rsync，要额外装。

### 3. 远端先 `command -v tar` 探测，无 tar 直接回退

**方案**：第 4 步前加一次探测；探测失败则走逐文件路径。

**为什么**：tar 是**性能优化**，不该成为新的单点故障。极老发行版 / busybox 环境可能没有
GNU tar，那时逐文件虽然慢但能用。

### 4. 解包后校验文件数，不符则失败

**方案**：`ls {batch}/*.md | wc -l` 与打包前的本地文件数比对，不一致 ⇒ 返回失败并清理批次目录。

**为什么**：tar 命令返回 0 只代表「解包过程没报错」，不代表「文件齐」。
**这正是本 change 要防的那类假信号** —— 不能在优化里再引入一个「看起来成功」。

### 5. tar 打包异常 ⇒ 自动回退逐文件

**方案**：`_pack_tar` 抛异常或返回 None 时，走原逐文件路径，并在 reason 里标注
「已回退逐文件模式」。

**为什么**：文件被占用（Windows 常见）、磁盘满、权限问题都可能让 tar 失败。
回退保证**功能不退化**。

### 6. 批次目录命名与远端布局完全不变

**方案**：仍是 `{node_id}-experiences-{YYYYmmdd-HHMMSS}`，tar 包解包后删掉。

**为什么**：服务器侧有扫描逻辑（消费方）依赖这个布局。改布局属破坏性变更，
与本 change 目标（提速）无关。

## Architecture

### 改造后的第 4 步

```
                        本地                                  远端
  ┌──────────────────────────────────┐
  │ out_dir/                         │
  │   EXP-001.md  EXP-002.md  ...    │
  │   （112 个）                      │
  └────────────┬─────────────────────┘
               │ _pack_tar()
               ▼
  ┌──────────────────────────────────┐
  │ /tmp/xxx/local-experiences-      │
  │  20261031-203459.tar.gz          │   ← 单个文件，arcname 扁平化
  └────────────┬─────────────────────┘
               │ scp（1 次协商）
               ▼
  ┌──────────────────────────────────┐      ┌──────────────────────────────┐
  │ ssh alias "mkdir -p batch_dir"   │─────►│ batch_dir/                   │
  └──────────────────────────────────┘      │   xxx.tar.gz                 │
                                            └──────────┬───────────────────┘
                                                       │ ssh "tar -xzf && rm"
                                                       ▼
                                            ┌──────────────────────────────┐
                                            │ batch_dir/                   │
                                            │   EXP-001.md ... EXP-112.md  │
                                            └──────────┬───────────────────┘
                                                       │ ls | wc -l
                                                       ▼
                                            校验 == 112 ? PASS : FAIL+清理
```

### 代码改动

| 位置 | 改动 |
|---|---|
| `_pack_tar(out_dir)` | **新增**：tarfile 打包到临时目录，返回 `(path, reason)` |
| `_scp_dir()` 第 4 步 | **替换**：`scp -r -- *files` → `scp -- <tar>` + `ssh "tar -xzf ... && rm ..."` |
| `_scp_dir()` 第 5 步 | **增强**：文件数与本地比对（原来只打印） |
| `_scp_dir()` 回退分支 | **新增**：tar 失败 → 逐文件（原逻辑保留为 `_scp_dir_files()`） |

### 保留不变

- `_validate_remote_path()` 三道白名单校验
- `-` 开头文件名拒绝
- `--` 终止选项解析
- SSH 可达性 + 目录可写探测
- 三档降级语义（scp → github → inbox）

## Risks / Trade-offs

| 风险 | 缓解措施 |
|---|---|
| 远端无 tar（极老发行版 / busybox） | 先 `command -v tar` 探测，无则回退逐文件；本机服务器已实测 GNU tar 1.35 |
| tar 内含路径穿越条目 | `arcname=basename` 强制扁平化（结构性免疫，不靠解包时校验） |
| 解包不完整被当成功 | 解包后 `ls \| wc -l` 与本地比对，不符则失败 + 清理批次目录 |
| 改 scp 破坏既有 15 个 transport 测试 | 先建基线（本文件已记录：`tests/test_share_ssh_transport.py` 15 用例）；改动后逐个复核，只改因实现变更必须改的断言并注明理由 |
| tar 打包本身失败（文件被占用/磁盘满） | 自动回退逐文件，reason 标注「已回退」 |
| 临时 tar 包残留 | `finally` 里删临时目录（沿用 `publish_via_scp` 的 `shutil.rmtree(ignore_errors=True)` 范式） |
| 压缩开销抵消收益 | 112 个 1-5KB 小文件压缩率约 60-70%，压缩耗时 < 0.1s，远小于节省的 112 次协商 |
