# 法定源收进工作区 - 技术设计

## Context

### 现状（上一轮 change `install-source-repo` 确立的架构）

```
   法定源  ~/.workbuddy-ai/Fstdd      ← 区外；skill 路径指向它
      │  git 双向同步
      ├────────  工作区 stdd-repo/      ← 开发副本
      └── push ──> GitHub DKK_Fstdd     ← 上传目标
```

**该架构的问题**：真源散落在**工作区之外**，与 D哥 2026-09-15 提出的
「所有开发形成的文件一律存放在工作区文件夹内」冲突。

### 为什么上一轮会那样定

上一轮的理由是「避免 skill 内路径固化到会话目录」——理由本身成立，
但代价（真源出工作区）当时未被权衡。D哥 现已裁定：**真源也要在工作区内**。

### 关键事实（实测，决定本 change 的成本）

按 git blob 哈希比对 `~/.workbuddy-ai/Fstdd` 与 `stdd-repo`：

| 分类 | 数量 | 处置 |
|---|---|---|
| 与 `stdd-repo` 逐字节相同 | 797 | 无需处理 |
| 内容在 `stdd-repo` 对象库中 | 13 | 历史版本，已被取代 |
| 「独有」 | 10 | 5 份已在上一轮归并；4 份是 `experiences/` 生成物；1 份旧快照 |

**且 `stdd-repo` 持有完整 git 历史（58+ 提交）与 tag**，而区外那份的 `.git`
是上一轮才初始化、内容来自 `stdd-repo`。

→ **`stdd-repo` 已是内容超集，收拢不丢任何东西。**

### 约束

- `D:/Programs/DKK_Fstdd` 是另一程序在用的调试副本，**全程只读**
- 区外副本**归档不删**（D哥 决定）
- 全量测试基线 **526 passed**，不得回归

## Decisions

### 1. `stdd-repo` 直接作为法定源，不新建目录

**方案**：确认工作区内的 `stdd-repo` 为唯一法定源，不另建 `fstdd-canonical/`。

**为什么**：它已在工作区内、已有全部 git 历史与 tag、已是内容超集。
新建目录会**增加**一个位置，与「收拢到工作区」的意图相反 ——
目标是**减少**位置，不是换个地方再放一个。

**备选方案及排除原因**：
- 备选 A：工作区内新建 `fstdd-canonical/` 作为法定源，`stdd-repo` 作开发副本 → 排除。
  多一个位置，且两者仍需同步，等于把上一轮的复杂度搬进工作区。
- 备选 B：保持法定源在区外，只往工作区放一份归档副本 → 排除。
  D哥 明确说「**包括真源**」，即要求真源本身在工作区。

### 2. 校验解析顺序回到「自定位优先」

**方案**：`FSTDD_INST_DIR` → 脚本自身 `tools/` → 工作区仓库 → 历史兜底。

**为什么**：**原则没变** ——「用**安装源自己的** verify 去校验」，因为被校验对象是
已安装的 skill，其内固化路径指向安装源。变的是**安装源是谁**：
现在是工作区仓库，而脚本就在工作区仓库里 → 自定位即命中安装源。

> 上一轮把它改成「法定源优先」是对的（当时安装源在区外）；
> 这一轮改回来也是对的。**同一条原则在不同架构下的必然结果**，不是反复。

**备选方案及排除原因**：
- 备选 A：保留「区外副本优先」→ 排除。区外副本将不再是安装源，用它校验会恒定误报。
- 备选 B：删掉解析逻辑，硬编码工作区路径 → 排除。会失去 `FSTDD_INST_DIR` 覆盖能力
  与独立部署场景的兼容性。

### 3. 归档用「复制」而非「移动」

**方案**：把 `~/.workbuddy-ai/Fstdd` **复制**到 `backups/`，**原目录保留**。

**为什么**：D哥 决定「归档不删」。复制 + 保留是唯一不会造成不可逆后果的做法；
且原目录仍被 7 个已安装 skill 的旧路径引用，直接移走会让旧 skill 立即失效
（虽然重装后会指向新路径，但过渡期不应留断裂）。

**验证**：归档前后文件数一致 + 逐文件哈希一致。

### 4. 重装放在解析顺序修正之后

**方案**：先改 `verify_*` 的解析顺序，再重装 skill。

**为什么**：重装后 skill 路径指向 `stdd-repo`，而 `verify_workbuddy_skills.py`
会据此校验。若解析顺序还停留在「区外优先」，它会去拿区外那份 verify，
而那份期望 skill 引用区外路径 → **恒定误报 FAIL**（本日已踩过同型问题）。
**顺序反了就会自造一次假失败。**

### 5. 文档与记忆同步更新

**方案**：更新 `docs/WORKBUDDY_INSTALL_NOTES.md` 第 0 节与项目 `MEMORY.md` 的法定源条目。

**为什么**：该文档正是「法定源在哪」这一判断的依据来源。它若仍写着区外，
下次任何人（包括我）都会按错的架构行动 —— 本日已多次因文档陈旧而误判。

## Architecture

```
   工作区  C:\Users\Administrator\WorkBuddy AI\2026-09-14-18-36-54\
   ┌──────────────────────────────────────────────────────────┐
   │  stdd-repo/          ← **法定源**（唯一权威；git 仓库；      │
   │                        完整历史 + tag fstdd-v1.0.0）        │
   │      │  安装脚本从这里读（SRC = stdd-repo/upstream）         │
   │      │  skill 内固化路径指向它                              │
   │      │                                                    │
   │      ├── push origin ──> GitHub DKK_Fstdd（上传目标）        │
   │      │                                                    │
   │      ├── backups/           ← 含区外副本的归档               │
   │      ├── .workbuddy-ai/     ← 记忆 / 临时                    │
   │      └── inbox/             ← 待审核池暂存（gitignored）      │
   └──────────────────────────────────────────────────────────┘
                    │ 安装
                    ▼
        ~/.workbuddy/skills/fstdd*   （AI 实际读到的；路径指向 stdd-repo）

   ⚠️ 区外 ~/.workbuddy-ai/Fstdd —— 已归档，不再是法定源（保留不删）
   ⚠️ D:/Programs/DKK_Fstdd     —— 另一程序的调试副本，全程只读
```

## Risks / Trade-offs

| 风险 | 缓解措施 |
|------|----------|
| **收拢时丢失仅存于区外的内容** | 归档前先按 git blob 哈希逐个比对（SC-002）；发现独有内容先归并再继续 |
| **skill 路径指向会话目录，会话目录变动后失效** | 这是本决定的**已知代价**（D哥 明确要求真源在工作区）。缓解：路径写绝对路径，且 `FSTDD_SRC`/`FSTDD_INST_DIR` 均可显式覆盖 |
| 解析顺序与重装次序反了，自造假失败 | Decision 4 明确先改顺序再重装；并有 SC-007 断言 |
| 归档操作不可逆 | 用**复制**而非移动（Decision 3）；原目录保留 |
| 误写 D 盘调试副本 | 全程只读；不动该目录 |
| 文档/记忆未同步，后续按旧架构行动 | SC-009/SC-010 显式断言 |
| 重装后旧 skill 与新区外副本不一致 | 原目录保留，旧路径仍可解析；重装即指向新路径 |
