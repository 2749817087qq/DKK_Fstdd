# 镜像失败告警 测试方案与详细案例

> 版本：v1.0
> 创建日期：2026-09-17
> 对应 Phase 2 Spec：`canonical/specs/code/2026-09-17-mirror-failure-alert.yaml`、`canonical/specs/agent/2026-09-17-mirror-failure-alert.yaml`

## 一、测试策略

### 1.1 测试金字塔

本变更是**运维可观测性**性质：产出一个钩子、一个标记文件、一条巡检命令、一个节点注册。
测试重心不在单元测试，而在**推送方视角的输出**与**端状态**：

- **静态/单元**（约 25%）：钩子 `bash -n` 语法、告警块文本结构、标记文件格式、
  推送命令审查（无 `--force`）、文档一致性
- **集成**（约 45%）：真实推送 → 推送方输出、标记写入/自动清除、巡检命令退出码、
  控制面节点注册与消息检索
- **E2E**（约 30%）：制造**真实镜像失败** → 全链路（回显 + 落盘 + 标记 + 控制面 + 巡检）
  → 恢复现场 → 验证标记自动清除

### 1.2 测试原则

- **从推送方视角断言** —— 本变更要消除的是"推送方以为推成功了"。只看服务器端状态
  （日志里有 `[WARN]`）**不算通过**，必须断言 `git push` 命令输出本身
- **看端状态，不看回显** —— 远端命令存在执行两次的环境特性，回显可能是两次中某一次的输出。
  结论以 `rev-parse` / `ls-remote` / `GET /messages` 为准
- **故障态测试必须恢复现场** —— agent spec 的 preconditions 已写明：模拟失败后必须把
  服务器恢复，不得留在故障态。每个失败态案例的收尾都要包含"恢复 + 标记清除"检查
- **验证"不做什么"** —— 否定式断言正是安全边界所在：
  不加 `--force`、不改钩子退出码、不因控制面不可达而整体失效、不在仓库留下凭证
- **幂等必须实测** —— 节点注册、部署脚本、巡检命令至少跑两次
- **告警路径必须被真实触发过一次** —— 实测 `mirror.log` 21 行 / WARN **0** 次，
  说明现有告警分支从未被验证。本方案的失败态案例不得用"读代码推断"代替真实触发
