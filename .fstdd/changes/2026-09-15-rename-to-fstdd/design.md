# 项目改名为 Fstdd（F=Fin）并独立于上游 - 技术设计

## Context

本项目（当前名 DKKstdd）是上游 STDD V3.0.5 的 WorkBuddy 本地化适配版，规模：

| 项 | 值 |
|---|---|
| upstream 代码 | 86 个 py 文件 / 671 文件 / 4.2M |
| `stdd` 字样出现 | 4728 处（其中 upstream 内 337 个文件） |
| `.fstdd` 字样出现 | 1939 处 |
| 需改名的标识 | skill 名 6 个、CLI 入口 1 个、环境变量 4 个、哨兵 1 个、数据目录 1 个、Python 包 1 个 |

**手工改名已失败一次**，失败形态值得记录：脚本按"逐条 `str.replace`"实现，规则
`STDD_SRC → FSTDD_SRC` 执行后，后续规则 `STDD → FSTDD` **又在自己的新串上匹配了一次**，
产出 `FFSTDD_SRC`。结果环境变量全部失效、隔离测试失败、并污染了真实 skill 目录。

这不是粗心，是**替换算法本身的缺陷**：多条 replace 顺序执行时，前一条的输出会进入后一条的输入域。

## Decisions

### 1. 替换采用「单次扫描」而非「逐条 replace」

**方案**：用一条正则 alternation 一次性匹配所有待替换串（长串在前），经
`re.sub(pattern, callback, text)` 完成替换。

**为什么**：`re.sub` 对原串**只扫描一遍**，替换结果不会重新进入匹配域 —— 从算法上
根除「自匹配」。逐条 `str.replace` 无法避免该问题，除非人为设计不可自匹配的规则集（脆弱）。

**备选方案及排除原因**：
- 备选 A：逐条 replace + 精心排序 → 排除。依赖人工推理"哪条会污染哪条"，规则一多必然出错；上次失败正是此路径。
- 备选 B：占位符中转（先 `STDD` → `\x00`，再统一替换）→ 排除。可行但引入不可见字符，调试困难，且占位符本身可能撞车。

### 2. 分层推进，而非一次性全量替换

**方案**：拆成 3 个垂直切片，每片独立可验证：

| 切片 | 内容 | 验证方式 |
|---|---|---|
| S1 标识层 | skill 名、环境变量、哨兵、项目名、文档 | `grep` 断言 + install 生成 skill 名正确 |
| S2 CLI 与包 | `bin/stdd`→`bin/fstdd`、`upstream/stdd/`→`upstream/fstdd/` | `fstdd --help` + init/new/status 冒烟 |
| S3 数据目录 | `.fstdd/`→`.fstdd/`（含迁移） | 迁移后 `fstdd status` 能列出两个归档 change |

**为什么**：三类改动的失败模式不同（S1 是文本误伤、S2 是 import 断裂、S3 是数据丢失），
混在一起做会让失败定位成本剧增。分层后每片的验证方式可以量身定制。

**备选方案及排除原因**：
- 备选：一次性全量替换 → 排除。上次已证明失败时无法定位是哪类改动出错。

### 3. 数据目录迁移采用「先备份、再改名、后验证」

**方案**：`git mv .fstdd .fstdd` 后，用 `fstdd status` 与 `ls .fstdd/archive/` 双重验证两个
已归档 change 仍可访问；迁移前先打 bundle 备份。

**为什么**：`.fstdd/` 下有 2 个已归档 change（含 test-report、proposal 等不可再生资产），
1939 处代码引用依赖该目录名。这是本次风险最高的一步。

**备选方案及排除原因**：
- 备选 A：保留 `.fstdd/` 不改 → 排除。用户明确要求全部改；且保留旧名会与同名实现的目录语义混淆。
- 备选 B：双目录兼容（同时读 `.fstdd/` 与 `.fstdd/`）→ 排除。增加长期维护负担，且掩盖迁移问题。

### 4. 上游同步机制改为「移除」而非「改造」

**方案**：`stdd-upgrade` skill 与 install 脚本中的上游同步逻辑改为自管理版本，
不再从 `leonai42/stdd` 拉取。

**为什么**：用户明确选择独立发展。保留半吊子的同步逻辑反而危险 —— 一旦误触发会把
上游的 `stdd` 命名覆盖回来，抹掉本次改名成果。

## Architecture

```
改动层次（自外向内）
┌─────────────────────────────────────────────┐
│ L1 用户可见标识                              │
│   skill 名 fstdd-*  │ 触发词 │ 文档 │ 项目名  │
├─────────────────────────────────────────────┤
│ L2 运行时标识                                │
│   CLI bin/fstdd │ 环境变量 FSTDD_* │ 哨兵     │
├─────────────────────────────────────────────┤
│ L3 代码与数据                                │
│   Python 包 upstream/fstdd/ │ 数据目录 .fstdd/ │
└─────────────────────────────────────────────┘

替换引擎（单次扫描）
  输入文本 ──► [正则 alternation，长串在前] ──► re.sub(callback) ──► 输出
                      │
                      └─ 单次遍历，替换结果不回流 ⇒ 无自匹配
```

## Risks / Trade-offs

| 风险 | 缓解措施 |
|------|----------|
| 替换误伤非标识用途的 `stdd`（注释、变量名、URL） | 正则加词边界；改完用 SC4 断言（除 upstream/ 与 .git 外无独立 stdd 残留）；参考 EXP-A4 教训——**必须跑真实数据看误伤，不能只看命中数** |
| Python 包改名导致 import 断裂，CLI 完全不可用 | S2 单独成片；改完立即跑 `fstdd --help` + init/new/status 冒烟；失败则回滚该片 |
| 数据目录改名后旧数据不可读，历史 change 丢失 | 迁移前打 bundle 备份；迁移后验证两个归档 change 可列出（SC5） |
| 替换后环境变量名畸形（如 FFSTDD_*） | SC1 专项断言：全仓库不得出现 `FFSTDD_`；由单次扫描算法从根上避免 |
| upstream 内部包名改动破坏第三方依赖路径 | 仅改包目录名与 import，不动功能逻辑；改完跑 CLI 冒烟覆盖主要命令 |
| 改名中途失败留下半成品状态 | 每片改完即 commit；有 pre-rename bundle 可整体回滚 |
