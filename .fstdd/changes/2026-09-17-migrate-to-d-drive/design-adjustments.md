## D1 — 完整性证据由「逐文件哈希」改为「树对象比对」

**偏离**：design.md Decision 3 定的证据是「逐文件哈希一致」。
实施后改用 **git 树对象比对**（`git rev-parse <commit>^{tree}`）。

**原因**：逐文件哈希会把**非内容文件**算进来，产生无法消除的假差异：

| 假差异 | 性质 |
|---|---|
| 我自己的哈希清单文件 | 自指（写清单这个动作本身改变了目录） |
| `.git/index` | git 的 **stat 缓存** —— 跑一次 `git status` 就会变 |
| `.git/refs/remotes/*` | 两边各自 fetch/push 历史不同，属**引用缓存** |

这些都不是「内容」，但逐文件哈希无法区分。**树对象比对天然只看内容** ——
git 的树对象由被跟踪文件的内容哈希构成，缓存与引用完全不参与。

**处置**：`test_a4_migration_captured_c_state` 用树对象比对；
另用 `git hash-object` 逐跟踪文件算指纹作为补充证据（首次验证时两者一致）。

**教训**：**完整性证据要选「只反映内容」的量**。文件数、逐文件哈希（含缓存）都会被非内容因素污染。

## D2 — 顺带修正 D 盘仓库的 C 盘引用

**偏离**：SPEC 未预见 —— 迁移后 D 盘仓库的 `.git/config` 里**仍指向 C 盘**。

**发现**：排查时列出 D 盘仓库的 remotes，发现两处 C 盘引用：

| remote | 指向 | 问题 |
|---|---|---|
| `local` | `C:/…/backups/stdd-repo.git` | 裸库在 C 盘 → 迁移后应指 D 盘 |
| `canonical` | `C:\…\.workbuddy-ai\Fstdd` | 已归档的区外副本，**已无意义** |

**处置**：
- `local` → 改指 `D:/tools/FSTDD/backups/stdd-repo.git`
- `canonical` → **移除**（它的同步对象已归档，留着只会误导）
- 顺带发现本地裸库**落后一个提交且缺 tag**（因最近几次是直推 origin、未走 push 脚本）→ 已补推

**教训**：**「迁移」不只是搬文件**。`.git/config` 里的 remote、凭证路径、
hooks 路径等**隐藏引用**同样要迁 —— 它们不在文件清单的显眼处，
但会让「迁移完成」变成假象。

## D3 — 迁移 `.gh_token`（由 D哥 提问才发现）

**偏离**：SPEC 未预见。

**经过**：D哥 问「GitHub 仓库是不是在 C 盘，在 C 盘的话也要迁移过去」。
排查结论：

- **GitHub 是远端服务器**（github.com），不在任何本地磁盘 → 无需迁移
- 但发现**三处指向 C 盘的本地引用**（见 D2），以及
  **`.gh_token`（GitHub 凭证，40 字节）位于 C 盘** `.workbuddy-ai/tmp/`

**为什么关键**：`.gh_token` 是 `share_experience.find_token()` 的凭证来源之一。
没有它，静默回传只能降级到自建端点通道（**丢 C 盘 = 失去 GitHub 直推能力**）。

**处置**：确认它**已随整体复制到 D 盘**（内容逐字节一致）。

**教训**：**凭证也是资产**。整目录复制天然覆盖了它，但值得显式验证 ——
若当初用「只复制仓库」的方案，凭证就会漏掉。

## D4 — 测试断言两次自我修正

### D4-a 「文件数一致」断言过脆

**现象**：`test_a3_file_count_matches` 反复失败（C=5386 vs D=5389）。

**根因**：两个目录**都在持续产生工作文件** —— 验证日志、提交信息、测试日志、
裸库的 pack 文件……任何一次运行都会改变计数。**与迁移完整性无关。**

**处置**：改为断言「关键资产存在」（归档目录、经验库、工具、文档、记忆等 8 项 +
归档 change 数量 ≥4）。真正可靠的证据交给树对象比对。

### D4-b 「内容一致」断言的**时点**错了

**现象**：`test_a4_tracked_content_identical` 在 D 盘更新文档后立即失败。

**根因**：断言写的是「D 盘**当前工作区** == C 盘**当前工作区**」——
但迁移之后 D 盘会继续开发，两份**理应分叉**。拿当前工作区比对，
**第一次开发就会误报**。

**处置**：改为比较「**迁移时刻那个提交的树对象**」在两边是否一致。
这才是「迁移是否完整捕获了源状态」的正确断言。

**教训（本日第三次）**：**断言的时点与范围必须与它要证明的命题对齐**。
前两次分别是：`test_fstdd_matrix` 硬编码日期（时点错）、
`test_migrate` 文件数（范围错，混入非内容文件）。
