### 3.1 本项暴露并修正了两个「假捕获」

**① 变异强度不足**

首轮变异只替换**首处**出现，导致 M1/M2/M3 被 `test_a6`（工作区干净）
而非目标断言捕获 —— 看着「已捕获」，实则**没验到该验的**。
修正为全部替换后，M1/M2 才由 `test_e1`/`test_e3` 正确捕获。

**② `test_d1` 的判据可被改名绕过**（真缺口）

M3 首轮**未被捕获**。根因：`test_d1` 判据是「不含 `WorkBuddy AI/2026-`」
这一**具体子串** —— 把路径改成 `C:/old-place` 就骗过了。
`test_d2` 的阈值「≥5 个」也太宽松。

**处置**：判据改为「凡含 `stdd-repo` / `FSTDD` 的绝对路径必须以 `D:` 开头」。
> 注意不能简单断言「无 C: 路径」—— skill 里的
> `"C:\Python311\python.exe"` 本身就在 C 盘，那是**工具**不是我们的资产。

**教训**：**「已捕获」不等于「被正确的断言捕获」**。
变异验证必须同时检查**捕获者是谁**，否则会掩盖断言的真实缺口。

## 四、关于「GitHub 仓库是否在 C 盘」（D哥 提问）

**结论：GitHub 是远端服务器，不在任何本地磁盘，无需迁移。**

但排查时发现**三处指向 C 盘的本地引用**，均已处理：

| 引用 | 处理 |
|---|---|
| `local` remote → C 盘裸库 | 改指 `D:/tools/FSTDD/backups/stdd-repo.git` |
| `canonical` remote → C 盘已归档副本 | **移除**（同步对象已归档，留着会误导） |
| **`.gh_token`（GitHub 凭证）** | 确认已随整体复制到 D 盘（内容一致） |

> `.gh_token` 是静默回传走 **GitHub 直推通道**的关键。丢了只能降级到自建端点通道。
> **凭证也是资产** —— 若当初用「只复制仓库」的方案，它会漏掉。

顺带发现本地裸库**落后一个提交且缺 tag**（因最近几次直推 origin、未走 push 脚本）→ 已补推。
