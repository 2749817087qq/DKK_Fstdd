# 待审核池到经验库的同步 - 技术设计

## Context

### 现状：链路到池子就断了

```
使用者机器 ──静默回传──> 自建端点待审核池 ──???──> Fstdd-experiences
   （已打通）              ~/fstdd-inbox          （无工具）
```

接收侧已验证可靠（17 条批量提交压成 1 次请求、429 自动重试后 17/17 落盘）。
**消费侧不存在** —— 池中数据只能靠人工 ssh 搬运：不可复现、无审核记录。

### 池中数据的实际形态（实测）

服务端落盘的文件名与内容：

```
文件名：EXP-00C0412F-20260916T025752Z.md          ← <experience_id>-<UTC时间戳>
内容：<!-- fstdd-inbox
      experience_id: EXP-00C0412F
      author: (anonymous)
      received_at: 2026-09-16T02:57:52.645214+00:00
      remote_addr: 27.8.11.15                      ← 投稿者 IP
      -->

      <正文>
```

### 两个必须处理的风险

1. **隐私**：`remote_addr` 是**投稿者 IP**。原样发布到公开仓库等于公开第三方个人信息。
2. **重复**：实测首轮 30 个文件里 13 个 id 各 2 份（同 id、不同时间戳后缀）。

### 可复用资产（先摸清再动手，避免重复实现）

`tools/share_experience.py` 已有：

| 能力 | 签名 | 用途 |
|---|---|---|
| 脱敏 | `sanitize(text, enabled=True) -> (文本, 命中规则)` | 入库前二次脱敏 |
| 凭证查找 | `find_token()` | 决定走直推还是降级 |
| 推送 | `publish(out_dir, repo, token) -> (bool, reason)` | **接受任意目录**，把其中文件推进经验库 `experiences/` 后 commit+push |
| 分批提交 | `publish_via_inbox(out_dir, url)` | 回传（本 change 不用，方向相反） |
| 文件筛选 | `export_files(out_dir)` | **排除 README.md / SUBMIT.md**（本日踩过的坑） |

> **关键发现**：`publish()` 接受**任意目录**，因此 `inbox_pull` 只需把待审核文件
> 拉到本地目录，推送**一行都不用重写**。

### 约束

- 不改动 `share_experience.py` 的行为（仅复用）
- 不改动接收端点（`inbox_server.py`）
- 全量测试基线 **503 passed**，不得回归
- 法定源已确立（`~/.workbuddy-ai/Fstdd`），本 change 的产物需同步到它

## Decisions

### 1. 拉取走 ssh+scp，而非给端点加「列取」接口

**方案**：`inbox_pull.py` 通过 `ssh`/`scp` 从服务器取回 `~/fstdd-inbox/*.md`。
主机与私钥可用 `FSTDD_INBOX_SSH_HOST` / `FSTDD_INBOX_SSH_KEY` 覆盖。

**为什么**：审核是**维护者专属**操作（不是使用者操作），维护者本就有 ssh 权限。
给端点加「列取/下载」接口会引入**新的鉴权面**（无鉴权则任何人可下载全部待审核内容，
含他人 IP），得不偿失。

**备选方案及排除原因**：
- 备选 A：给端点加 `GET /api/inbox` 列表接口 → 排除。需要鉴权，否则泄露所有投稿者 IP；
  加鉴权又要引入密钥分发，复杂度远超收益。
- 备选 B：把池子改成直接写进一个 git 仓库 → 排除。会改动已稳定运行的接收侧（本 change 范围外）。

### 2. 发布前**整体剥离**元数据头，而非逐字段删除

**方案**：解析出头字段供本地审核展示后，构造发布物时**把整个 `<!-- fstdd-inbox -->` 块删掉**。

**为什么**：逐字段删除容易漏（将来服务端加了新字段就会漏）。整体剥离是**结构性**保证 ——
只要头被删了，无论里面有什么字段都不会外泄。

**验证**：反向断言 —— 构造含 `remote_addr: 203.0.113.7` 的输入，断言发布物中该字符串出现 **0** 次。

### 3. 两级去重：先按 id 归一，再按内容哈希

**方案**：
- 一级：文件名归一为 `<experience_id>.md`，同 id 取 `received_at` 最新
- 二级：按正文内容哈希去重，内容相同的不同 id 只保留一份

**为什么**：只做一级无法处理「同一段经验被不同 id 重复提交」；
只做二级则无法处理「同 id 内容被修改过」的情况。两级互补。

**幂等**：两级去重都是**确定性**的（取最新 / 取哈希首见），重复执行结果一致。

### 4. 推送复用 `publish()`，零新实现

**方案**：把归一+剥离后的文件放进暂存目录，直接调 `share_experience.publish(staging, repo, token)`。

**为什么**：`publish()` 已处理 clone → 覆盖写入 → commit → push 全链路，且已修正
「误推 README.md/SUBMIT.md」的问题。重写一遍只会再引入一遍同类 bug。

**静态断言**：SC-010 要求「`publish()` 的定义处数 = 1」，防止日后有人内联复制一套。

### 5. 拒绝 = 移入 `rejected/`，不删除

**方案**：`--reject <id>` 把文件移入暂存目录下的 `rejected/` 子目录。

**为什么**：删除是不可逆的，而审核判断可能出错。留痕让人能事后翻查「当初为什么拒了」，
也便于发现「某类内容反复被拒」进而改进脱敏或提示。

### 6. 发布物只含经验文件

**方案**：构造发布物时用既有 `export_files()` 的排除规则，剔除 `README.md` / `SUBMIT.md`。

**为什么**：本日已踩过这个坑（`publish` 与 `publish_via_pr` 曾用 `glob("*.md")`
把说明文件一起推进经验库）。暂存目录同样会生成 README（审核索引），必须排除。

## Architecture

```
  ┌─ 自建端点（维护者专属操作）───────────────────────────────┐
  │  ubuntu@43.134.236.80:~/fstdd-inbox/*.md                 │
  │    <experience_id>-<UTC时间戳>.md  + <!-- fstdd-inbox --> │
  └──────────────────────┬──────────────────────────────────┘
                         │ ssh + scp（维护者凭据）
                         ▼
  ┌─ tools/inbox_pull.py ───────────────────────────────────┐
  │  1. pull    → 取回原始文件到 inbox/raw/                   │
  │  2. parse   → 提取 id/author/received_at/remote_addr      │
  │               （仅供本地审核展示）                          │
  │  3. normalize → <experience_id>.md，同 id 取最新           │
  │  4. dedupe  → 按正文哈希二次去重                           │
  │  5. strip   → 删除整个 <!-- fstdd-inbox --> 头            │
  │  6. sanitize→ 复用 share_experience.sanitize()            │
  │  7. review  → 输出审核表                                   │
  │  8. reject  → 移入 rejected/（留痕）                       │
  └──────────────────────┬──────────────────────────────────┘
                         │ 复用 share_experience.publish()
                         ▼
        2749817087qq/Fstdd-experiences（我方位置）

  ⚠️ 发布物不得含 remote_addr（投稿者 IP）、README.md、SUBMIT.md
```

## Risks / Trade-offs

| 风险 | 缓解措施 |
|------|----------|
| **投稿者 IP 被公开** | 整体剥离头（结构性保证）；反向断言「IP 出现 0 次」 |
| 剥离时误删正文 | 断言正文除脱敏替换外逐字保留 |
| 去重把不同经验误判为重复 | 一级按 id、二级按**内容哈希**；哈希相同即内容确实相同 |
| 重复拉取造成重复入库 | 归一命名 + 确定性去重 → 幂等；另有既有归一命名兜底 |
| 复用 `publish()` 时把索引文件推上去 | 复用 `export_files()` 的排除规则；加断言 |
| 端点不可达时静默成功 | SC-003 要求非零退出码 + 明确原因 |
| 给端点加接口引入新鉴权面 | **不加接口**，走维护者 ssh（Decision 1） |
| 审核表信息不足，无法判断 | 表含 id/作者/接收时间/字节/脱敏命中/重复情况 |
