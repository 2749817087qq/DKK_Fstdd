# 静默失效系统性排查 - 技术设计

## Context

FSTDD 自有层（`upstream/fstdd` + `tools/`）存在 29 处「`except [Exception]` 块
首语句为空操作（pass/continue/空返回）」的点位（2026-09-18T08:34+08:00 实测，
HEAD 6c5d390）。其中 guard.py 6 处、status.py 3 处、check_timestamps.py 3 处；
文件名含检测语义的 11 处 / 4 个文件。

2026-09-17 的 EXP-20260917-B3 已实证该类点位的最坏形态：`_dt.timezone.utc`
误写被 `except Exception: pass` 吞掉，guard 僵尸/卡壳检测**长期全哑**直到
全量回归才暴露。当前没有任何机制区分「故意容错」与「意外吞错」，
也没有行为级证据证明关键检测「红的时候真的会红」。

技术栈：Python 3.11/3.13，pytest 7.4。约束：改动不得改变既有检测的判定语义；
审计工具只读；合理容错不为清零而删。

## Decisions

### 1. 审计分类三态：每处点位必须有结论和理由

**方案**：29 处逐点审计，结论必为三类之一：
- `intentional`（合理容错）：探测类操作失败返回 None/False，调用方有显式分支处理
- `bug`（意外吞错）：except 掩盖了本应暴露的缺陷（如 B3），修复 + 补测试
- `narrow`（需收窄异常类型）：容错意图正确但 `except Exception` 过宽，收窄到具体类型

**为什么**：「清零」既不现实也不正确——探测类容错是正常工程模式（约束明确：
合理容错不得为了清零而删）。价值在于**强制逐点表态**：没有「没看过」这个选项。

**备选方案及排除原因**：
- 全部消除裸 except：误伤探测类容错，改变行为语义，违反约束
- 只审检测语义文件（11 处）：非检测函数的吞错同样会掩盖缺陷（B3 的
  upgraded_at 就在 upgrade.py），且新检测逻辑会诞生在非检测文件里

### 2. 变异测试是「检测在干活」的唯一行为级证据

**方案**：对关键检测路径各建 ≥1 个变异测试——注入一个**已知必触发该检测**
的缺陷，断言检测报出；`try/finally` 恢复现场后断言检测恢复绿。
每个变异测试双自证：注入后必红、恢复后必绿，缺一即测试本身无效。

**为什么**：静态检查只能证明「形态对」（B3 证明形态对语义照样错）；
只有行为证据能证明「检测真的会响」。这是「测试绿了 ≠ 断言有效」
项目经验的直接应用。

**备选方案及排除原因**：
- 只补正常路径单测：B3 的 guard 两处有正常路径覆盖也照样全哑——
  问题不在覆盖率，在断言的有效性
- 打桩替代真实缺陷：变异测试要的是**真实代码路径上的真实缺陷**，
  桩掉关键调用等于没测

### 3. 防回潮工具 audit_silent_except.py + 豁免清单入仓

**方案**：`tools/audit_silent_except.py` 枚举吞异常点位（口径与 Gate 1 盘点
一致），对照**入仓豁免清单**（`.fstdd/audit-exceptions.yaml`，每条含
文件/行号/锚点/分类/理由/审计日期）报告「清单外的新增点位」。
行号漂移容忍：文件相同 + 行号 ±5 + 锚点上下文（点位所在函数名）匹配
即视为同一处。CI 集成：挂到 `fstdd ci` 检查链路（与 verify_eol 同层）。

**为什么**：人肉记得检查不可靠（EXP-20260915-B2 的复发模式）；
清单入仓让「豁免」也成为被 review 的产出物，理由必填防止「打个标记就逃」。

**备选方案及排除原因**：
- 只写文档规范不造工具：A1/B3 的教训——规范不产生约束力，工具才产生
- pylint 等现成静态规则：只能查「有没有 except」，查不了「这处容错
  是否有理由」这个语义判断

### 4. except 留痕规范：检测/校验函数禁止裸 pass

**方案**：本 change 修复的点位统一留 `logger.debug` 痕迹（最低限度）；
规范写入 stdd-build 验收清单（与变异测试要求并列）。审计工具对
「检测语义文件中的裸 pass except」单独标级——存量中已判 intentional 的
不强制返工，但**新增**必须留痕。

**为什么**：让异常至少可见——B3 的 except 里若有一行 debug 日志，
发现时间会从「全量回归才暴露」缩短到「第一次执行就看到」。

### 5. 审计范围与测试文件的处置

**方案**：扫描范围 = `upstream/fstdd` + `tools/`（与盘点一致）。
`upstream/tests/` 中的同类点位**纳入审计但单列分类**（测试容错多为
夹具清理，以 intentional 为主）；`backups/`、`deliverables/` 明确排除。

## Architecture

```
tools/audit_silent_except.py
  ├─ scan():      遍历 upstream/fstdd + tools/ 的 .py，枚举 except-空操作点位
  ├─ load_exemptions(): 读 .fstdd/audit-exceptions.yaml
  ├─ match():     点位 ↔ 豁免（文件 + 行号±5 + 函数锚点）
  └─ report():    清单外点位 → 非零退出 + 明细（文件:行 + 所在函数 + 首语句）

.fstdd/audit-exceptions.yaml（入仓，人工维护）
  - file / line / anchor(函数名) / category(intentional|bug-fixed|narrowed)
    / reason（必填）/ audited_at / audited_by

tests/test_mutation_<target>.py（每个关键检测路径 ≥1）
  注入已知缺陷 → 断言检测报出（必红）→ finally 恢复 → 断言恢复绿
```

## Risks / Trade-offs

| 风险 | 缓解措施 |
|------|----------|
| 审计中再发现已哑检测，修复引发连锁测试红 | 预期内；逐处按 TDD 处理，审计顺序「检测语义优先」 |
| 行号漂移致豁免匹配失效、CI 误报 | 锚点函数名 + 行号容差；误报时更新清单条目（留痕） |
| 变异测试自身写错造成假信心 | 双自证（注入必红 + 恢复必绿），自证失败则该测试无效 |
| 收窄异常类型后漏掉原宽 except 兜住的异常 | narrow 处补「异常类型确认」用例：构造原宽 except 接住的异常，断言窄 except 下行为符合意图 |
