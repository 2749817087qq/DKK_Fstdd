# 工作台自包含（目录联接）问题群 — 2026-09-21

> 场景：`D:\项目\工作台` 要做成**自包含**（「不要代码散了」），
> 约束是 **只搬引擎代码、数据留原地**、**只搬工作台、不动别的项目**。
> 方案：把 4 个引擎模块复制进 `工作台\engine\`，并在代码旁挂 **NTFS 目录联接**
> 指向真实数据（`wechat-archiver\*`），让引擎里
> `Path(__file__).resolve().parent` 派生的常量零修改生效。
>
> 本轮在这一条线上**连出 7 个问题**，其中 1 个造成**真实数据丢失**。
> 单条经验见 `experiences/FSTDD003-EXP-20260921-JUNCTION-1.md`；
> 本文是成体系的问题清单与固化动作。

## 0. 一句话结论

> **「把代码搬走、数据留原地」这个需求，最容易踩的不是架构，是文件系统语义。**
> 目录联接在 `is_dir()` / 遍历 / 递归删除上**与普通目录完全同形**，
> 所有「看起来显然」的判断（存在即跳过、递归删除、字符串比较、`islink`）
> 在这里**全部失效**，而且失效方式是**静默的**。

## 2. 深挖：P32 是本轮唯一造成真实数据丢失的一条

### 复现

```powershell
New-Item -ItemType Junction -Path <probe> -Target <real_data>
Remove-Item -Recurse <probe>          # ← 致命
```

输出：

```
Remove-Item : ... 目录不是空的 ... SAFE_DELETE_FAIL_CLOSED
```

**看起来是「删不掉」，实际是「删了一部分之后失败」。**
事后核对：`<real_data>` 里 **1015 个真实文件已消失**。

### 为什么

目录联接（`IO_REPARSE_TAG_MOUNT_POINT`）对 `Path.is_dir()` 为真、对目录遍历透明，
因此**递归删除会穿透联接去删目标内容**。
（对照：POSIX 符号链接不会；Windows 符号链接也不会。**只有「联接 + 递归删除」这个组合会**。）

### 正确写法

```python
os.rmdir(link)                                  # → RemoveDirectoryW，只摘重解析点
[System.IO.Directory]::Delete($link, $false)    # 同上，$false = 不递归
```

### 为什么这条特别危险

**错误操作返回的是「失败」，而失败让人以为「什么都没发生」。**
实际是部分删除 + 静默数据丢失。这比「成功删除了不该删的东西」更难察觉 ——
后者至少后果明确。

## 3. 深挖：P37 为什么必须「退回」而不是「返回空」

引擎目录没就绪（没跑引导脚本、或联接被误删）时，有两种写法：

| 写法 | 后果 |
|---|---|
| `return ENGINE_DIR`（不存在） | 所有读数据接口拿到空目录 → **返回 0 条、不报错** → 界面显示「没有文章」→ 用户以为功能没做 |
| `return REAL_ROOT`（兜底） | 功能**照常可用**，只是少了一层自包含；同时 `health_warnings()` 明确报「已退回真实数据根」 |

选后者。**这是本项目反复踩过的同一类事故**：
`modules/_paths.py` 开头就写着「路径不存在 → 所有读数据的接口静默返回空（不报错，只是没数据，极难排查）」。

配套：`engine_ready()` 必须**同时**查两个条件 ——
只查「代码在」→ 联接没建时静默空；只查「数据在」→ 代码没搬时 import 失败。
**少查一个都会把「没配好」伪装成「没数据」。**

## 6. 可复用的判断（写进方案模板）

1. 「代码搬走 + 数据留原地」优先选**联接**而非改代码 ——
   当数据路径由 `Path(__file__)` 派生时，改代码会让副本与上游**永久分叉**。
2. 但选了联接就必须接受：**所有文件系统操作都要重新审一遍**。
   尤其：递归删除、字符串比较、`is_dir()` 判据、git 索引。
3. **凡「按路径判断是否已就绪」的逻辑，都必须能区分「没配好」与「没数据」。**
   这是本项目第三次踩到同一类事故。
4. **验证脚本必须能自己发现联接缺失**，不能等报错。
5. 删除类操作**先校验对象类型**（是不是联接），再删；
   并把「拒绝删除」做成显式异常，而不是静默跳过。

## 7. 补验发现 P39：兜底只在**进程启动时**生效

落地后补做了一项验证：**拆掉全部目录联接，模拟「刚克隆下来」**。
结果一半好、一半坏。

### 好的那一半（设计预期成立）

```
【模拟刚克隆：进程启动前联接就不在】
  新进程 import -> self_contained=False
                   archiver=D:\...\wechat-archiver（真实数据根）
                -> 功能完全正常，只是不再自包含
  python tools\setup_engine.py  -> 4 个 [new]，一键复原
  python tools\setup_engine.py --check -> 全 [ok]
```

### 坏的那一半（新缺陷 P39）

```
【服务已经在跑，此时删掉 engine/data 联接】
  GET /api/health                              -> status=ok     （什么都没变）
  GET /api/wechat/articles?only_unfetched=true -> total=0       （真实是 2）
  日志干净，无异常，无 5xx
```

**根因**：`ARCHIVER` / `SELF_CONTAINED` 是**模块导入时**算好的常量。

```python
ARCHIVER = resolve_archiver()      # ← 导入那一刻定死，之后不再求值
DATA_DIR = ARCHIVER / "data"
```

进程启动时联接是好的 → `ARCHIVER = 工作台/engine`。之后联接被删，
进程仍拿着 `engine/` 往下拼 → 目录不存在 → 各模块的读取逻辑
（`Path.glob` / 兜底）**返回空列表而不是抛错** → 静默。

⇒ **兜底的作用域被默认成了「整个生命周期」，实际只有「启动那一刻」。**

### 处理：不自愈，但让它可见

**没做运行期自愈**，因为要把 5 个模块里的路径常量全改成函数
（`ARCHIVER / "data"` 这种写法到处都在，模块间还互相 import），
改动面大、回归风险高；而触发条件只是「运行中手工删联接 / 跑 `--remove`」这种维护动作。
**性价比不成立。**

改为：`_paths.live_status()` **每次调用重新探测** + `/api/health` 暴露 `degraded`，
`degraded` 时 `status` 也变成 `degraded`。

🔴 **告警文案必须区分两种「未就绪」** —— 两者后果相反，混成一句会把排查方向带偏：

| 情形 | 事实 | 文案 |
|---|---|---|
| 导入时就未就绪 | 已退回真实数据根，**功能是好的** | 「已退回真实数据根，功能可用但工作台不再是自包含的」 |
| 导入后联接才丢 | 本进程仍指着坏目录，**会返回空** | 「本进程仍指向该目录，读数据接口会返回空（不是没数据）——重建联接后立即恢复，无需重启」 |

判据：`ARCHIVER == resolve_engine()`。

实测结果：

| 阶段 | `status` | `degraded` | 未抓取 |
|---|---|---|---|
| 正常 | `ok` | `false` | 2 |
| 运行中拆 `engine/data` | `degraded` | `true` | 0（缺口仍在，但已可见） |
| 重建联接（**不重启**） | `ok` | `false` | 2 |

测试 23 → 27 条（`TC_SC_040–043`），全量 207 → **211 passed**。

### 🔴 本轮最大元教训

> **验证一定要跑「坏掉」的分支。**
> P39 是「模拟刚克隆」这个动作顺带拆掉联接才撞见的 ——
> 只跑 happy path 永远不会发现。
>
> 凡是「配置兜底」，都要问一句：
> **它从什么时候开始生效、到什么时候失效？**
> 「启动时求值一次的常量」天然不具备运行期兜底能力，
> 而它的失败方式恰恰是**最安静的**（返回空，不报错）。
>
> 以及：**同一句状态告警，在不同时刻可能是假的。**
> 「已退回真实数据根」在运行期场景下就是假的（本进程并没退回），
> 照着它去查会南辕北辙。

## 8. 补验的另一半：把「建/修」动作放进启动链

§7 只解决了「**坏掉之后看得见**」。**「还没配好」这一半同样是静默的**，
只是方向相反：

```
克隆/换机后没跑 setup_engine.py
  -> 进程启动时就未就绪 -> 兜底退回真实数据根
  -> 功能完全正常、界面完全正常、health 也是 ok
  -> 用户完全不知道「工作台已经不是自包含的了」
```

**兜底把「配置缺失」变成了「正常工作」，于是它不再有任何信号。**

### 修法

`tools/launch.py` 新增 `ensure_engine()`，启动链变 5 步：

```
[1/5] 桌面快捷方式（COM，自愈）
[2/5] 引擎自包含（建/修目录联接）      ← 新增
[3/5] 检查依赖
[4/5] 检查系统代理
[5/5] 启动服务
```

于是**双击即用**，「忘了跑 setup」不再有任何隐性代价。

**前提：修复脚本必须幂等且绝不破坏现有状态** ——

- 已是正确的联接 → 跳过
- 目标位置是**真实目录**（不是联接）→ **拒绝覆盖并报错**，绝不删
- 删除联接只用 `os.rmdir()`

满足这三条才能安全放进启动链。
**不幂等的修复脚本放进启动链 = 每次启动做一次危险操作。**

### 补的测试

- `TC_SC_050`：启动链必须含 `setup_engine.py` + `ensure_engine(py)` 被调用
  + 步骤编号 `[1/5]…[5/5]` 连贯。
- `TC_SC_051`：**真的拆掉一个联接 → 调 `ensure_engine()` → 验证修得回来**
  （`finally` 兜底复原）。只断言「源码里有这行」是**假绿**（P21 类关键词断言）。

全量测试 211 → **213 passed**。

### 复用要点

> **凡引入兜底，就要同时把幂等的配置修复动作放进启动链。**
> 否则兜底越完善，配置缺失越没有信号。
