### A2d 智能分组理由

1. **S1 独立成切片**：全部纯函数、零副作用、可用内存 fixture 测试，是唯一能在**不碰任何数据**的前提下验证核心逻辑（公式、三重守卫、计数口径）的切片。必须最先做。
2. **S2 与 S3 分离**：JSON 写入与 PG 写入是两条独立写入路径（Decision 1），失败模式不同（前者怕写坏真源，后者怕事务不完整），分开验证。
3. **S4 独立**：编排改动只碰 `daily_etl.py` 一个文件，与脚本逻辑正交。
4. **S5 为集成收口**：所有破坏性操作集中在一次受控执行中完成，避免多次写生产库。

## 切片清单

- **实现目标**：`load_calendar()` / `plan_purge()` / `plan_return_fills()` / `plan_amount_fills()` / `build_plan()`
- **产出文件**：`repair_kline_fields.py`（骨架 + 纯函数部分）
- **覆盖 TC**：TC-KFB-001 / 002 / 006 / 008 / 010 / 011（6 个）
- **覆盖 Scenario**：SC-001-001 / 001-002 / 002-004 / 003-002 / 004-002 / 004-003
- **验证方式**：内存 fixture，**不触碰任何真实数据**
- **风险**：🟢 低

### S2｜JSON 写入层

- **实现目标**：`apply_to_json()`（原子写 + 备份 + coverage）、`--write` / `--purge-phantom` 授权门、dry-run 默认
- **产出文件**：`repair_kline_fields.py`（写入部分）
- **覆盖 TC**：TC-KFB-013 / 014 / 019 / 020 / 021 / 022（6 个）
- **覆盖 Scenario**：SC-005-001 / 005-002 / 008-001 / 008-002 / 009-001 / 009-002
- **验证方式**：`--json <tmp>` 在临时副本上跑真实代码路径
- **风险**：🟢 中低（临时副本隔离）

### S3｜PG 应用与一致性

- **实现目标**：`apply_to_pg()`（单事务 UPDATE×2 + DELETE×1）、`verify()`（三项计数断言）
- **产出文件**：`repair_kline_fields.py`（PG 部分）
- **覆盖 TC**：TC-KFB-015 / 016（2 个）
- **覆盖 Scenario**：SC-006-001 / 006-002
- **验证方式**：只读断言（写库由 S5 一次性执行）
- **风险**：🟡 高（破坏性，但本切片只写不跑）

### S4｜编排集成

- **实现目标**：`daily_etl.py` 新增 `SOURCES["repair_kline"]` + `run_repair_kline()` + 插入 `DAILY_DEFAULT`
- **产出文件**：`daily_etl.py`（1 处 SOURCES 条目 + 1 个函数 + 1 处列表 + 1 处 if 分支）
- **覆盖 TC**：TC-KFB-017（1 个）
- **覆盖 Scenario**：SC-007-001
- **验证方式**：`daily_etl.py --dry-run` 检查顺序
- **风险**：🟢 中低

### S5｜一次性受控执行与结果断言

- **实现目标**：在**取得 D哥确认后**依次执行 `--write` → `--purge-phantom --write` → `--apply-pg --verify`，再跑完整 `daily_etl.py` 验证不回滚
- **产出文件**：`backups/phantom_<ts>.csv`、`backups/reits_kline_daily_<ts>.json`、更新后的 JSON 与 PG
- **覆盖 TC**：TC-KFB-003 / 004 / 005 / 007 / 009 / 012 / 018 / 023（8 个）
- **覆盖 Scenario**：SC-002-001 / 002-002 / 002-003 / 003-001 / 004-001 / 004-004 / 007-002 + proposal §1.5
- **验证方式**：全量只读断言
- **风险**：🟡 高（**写生产库 + 删行，执行前须再次确认**）
