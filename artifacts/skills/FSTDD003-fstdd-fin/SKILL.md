# FSTDD-Fin · 金融规驱

> **这不是两份文档的拼接。**
> `fintech-engineer` 给的是「金融系统该有什么」——一堆领域清单；
> FSTDD 给的是「怎么保证它真的被做对」——流程与验证。
> 本 skill 把前者**逐条翻译**成后者流程里的**强制规格项与验收项**：
> 清单上的每一条，要么在 SPEC 阶段变成可测试的规格，要么在 DELIVER 阶段变成打勾项。
> 落在流程之外的知识 = 不会被执行的知识。

## 1. 金融系统红线（一票否决，贯穿全流程）

| # | 红线 | 违反后果 |
|---|------|---------|
| 1 | **交易准确性 100%**：金额用 Decimal，禁止 float 参与金额运算，舍入模式显式指定 | Gate 不通过 |
| 2 | **幂等性**：所有写操作（支付、扣款、下单）必须支持幂等键，重复请求不产生重复结果 | Gate 不通过 |
| 3 | **审计不可篡改**：关键操作日志 Append-only、含输入输出/时点/操作者/来源，可回放 | Gate 不通过 |
| 4 | **账实相符**：必须有对账机制（内部账 vs 渠道账），差异必须可发现、可追踪 | Gate 不通过 |
| 5 | **降级不静默**：外部依赖（支付网关/银行接口/行情源）不可用时，必须显式标记 + 告警，**禁止**用脏数据/过期数据静默出结果 | Gate 不通过 |
| 6 | **数据合规**：KYC/AML、数据留存期限、数据驻留地、隐私法规，按辖区明确 | 合规验收不通过 |
| 7 | **无硬编码凭据与常量**：密钥/证书/费率/限额一律走配置或密钥管理，不进代码与版本库 | 安全验收不通过 |

> 红线 5「静默降级」是金融系统最隐蔽的杀手：系统看起来在正常出结果，
> 实际用的是过期或残缺数据。**任何降级都必须显式且可告警。**

## 2. 四阶段 · 金融增强

### P1 UNDERSTAND — 需求理解（金融版必答项）

在标准 proposal 之外，**逐项明确**才允许进入 P2（缺一项 = Gate 1 不通过）：

| 必答项 | 说明 |
|--------|------|
| **系统类型** | 支付 / 银行集成 / 交易撮合 / 风控反欺诈 / KYC-AML / 开放银行 / 加密-DeFi，还是组合？ |
| **监管辖区** | 哪些国家/地区？适用哪些法规（PCI DSS、AML、GDPR/个保法、数据驻留要求）？ |
| **合规要求** | 是否需要 PCI DSS 认证？KYC/AML 到什么程度？可疑活动上报？留存多久？ |
| **量级与性能** | TPS 峰值？延迟要求（如 <100ms）？可用性目标（如 >99.99%）？ |
| **集成点** | 接哪些外部系统（支付网关、核心银行、行情源、KYC 供应商）？协议与 SLA？ |
| **资金与币种** | 单币种还是多币种？结算周期？是否涉及跨境、稳定币、法币兑换？ |
| **降级策略** | 每个外部依赖不可用时怎么办？（**必须逐条填，不许留白**） |

### P2 SPEC — 规格设计（金融版核心增值）

除常规 design.md + specs + test-plan.md，**强制新增三份契约**：

#### 2.1 数据契约（Data Contract）

每个数据项一行：指标名 / 来源 / 口径 / 时点 / 类型精度（如 `Decimal(18,6)`）/ 更新频率 / **降级行为**。
**降级行为未填 = 规格不完整**，禁止进入 P3。

#### 2.2 口径定义表（Glossary）

把所有歧义写死：

- 金额：币种、精度、舍入模式（ROUND_HALF_UP / ROUND_DOWN）、是否含税含费
- 时间：时区、结算日 vs 自然日、交易日日历来源、日切时刻
- 余额：可用余额 vs 账面余额、是否含在途冻结
- 费率：谁承担、何时扣、跨行/跨境如何算
- 状态机：交易/订单的每个状态与合法迁移（含失败与冲正路径）

#### 2.3 合规与审计契约（金融版独有）

| 项 | 内容 |
|----|------|
| 审计字段 | 哪些操作必须留痕？留哪些字段？留存多久？ |
| 幂等约定 | 幂等键由谁生成？作用域？有效期？冲突如何处理？ |
| 对账规则 | 对账频率、对账口径、差异容忍度、差异处理流程 |
| 数据合规 | PII 字段清单、加密/脱敏策略、留存期限、跨境传输限制 |
| 上报义务 | 是否需可疑交易上报？阈值？时限？ |

**Gate 2**：三份契约经用户确认后锁定。没锁死就开工，后面必然返工——
金融系统的返工成本远高于写契约的成本。

### P3 BUILD — 实现（金融版硬规则）

以下为**强制项**，不是建议：

**资金与数据**
1. 金额一律 `Decimal`，禁止 float；舍入模式显式指定，不用默认
2. 时间一律带时区，内部 UTC，展示层转目标时区，禁止 naive datetime
3. 状态机显式化，禁止用散落的 if-else 表达业务状态
4. 外部数据获取必须可注入（mock 是自动化降级测试的前提）

**可靠性**
5. 写操作幂等（幂等键 + 唯一约束 + 冲突检测）
6. 分布式事务用 Saga / 事件溯源，不用裸分布式事务
7. 外部依赖加熔断 + 超时 + 重试（重试必须幂等且带退避）
8. 关键路径可回放：事件日志完整，能重放出任一时刻状态

**安全与合规**
9. 全链路 TLS，静态加密，密钥走密钥管理（不进代码）
10. 最小权限 + 零信任，API 认证 + 限流
11. PII 加密/脱敏，按契约留存，到期可删除
12. 审计日志 Append-only，禁止 update/delete

**可观测**
13. 交易监控、性能指标、错误追踪、合规告警、SLA 监控
14. 业务指标可度量：准确率、成功率、延迟分位、对账差异数

### P4 DELIVER — 交付（验收清单）

交付前逐项打勾，缺一不可：

- [ ] 金额精度与舍入正确（有测试证明）
- [ ] 幂等性验证通过（重复请求、并发重复）
- [ ] 对账机制可用，差异可发现可追踪
- [ ] 审计日志完整且不可篡改，可回放
- [ ] 降级路径已实现且已测试，无静默降级
- [ ] 合规项达标（按 P2.3 契约逐条对照）
- [ ] 安全项达标（加密、认证、限流、无硬编码凭据）
- [ ] 灾备方案就绪，恢复演练有记录
- [ ] 文档完备（架构、接口、运维 Runbook、监管备查材料）

## 3. 金融系统特有测试维度（测试方案必含）

在常规单测之外，**必须**覆盖：

| 维度 | 测什么 |
|------|--------|
| **幂等** | 重复请求、并发重复请求、网络重试、幂等键冲突 |
| **对账** | 账实相符、跨渠道对账、差异注入后能否发现 |
| **精度** | 极大值、极小值、0、负数、舍入边界（如 0.005）、多币种换算 |
| **时区/日历** | 跨时区、夏令时、交易日 vs 自然日、日切时刻（23:59:59.999） |
| **降级** | 依赖超时 / 返回空 / 返回脏数据 / 返回乱序 / 部分成功 |
| **一致性** | 并发扣款、余额不超卖、库存/额度不穿透 |
| **安全** | 越权访问、重放攻击、参数篡改、注入 |
| **审计** | 日志完整性、不可篡改、可回放 |
| **合规** | KYC 拒绝场景、AML 命中、名单筛查、留存期限 |
| **恢复** | 中断后继续、冲正回滚、数据修复 |

## 4. 失败模式（金融系统特有）

| 模式 | 表现 | 拦截点 |
|------|------|--------|
| **重复扣款** | 幂等失效，重试导致多次扣款 | 幂等测试 + 唯一约束 |
| **账实不符** | 内部账与渠道账对不上，无人知晓 | 对账测试 + 差异告警 |
| **静默降级** | 依赖挂了仍出结果，用的是过期/残缺数据 | 降级测试 + 显式标记（红线 5） |
| **精度丢失** | float 算钱，累计误差 | Decimal 强制 + 精度测试 |
| **审计缺口** | 日志可改/缺失，出事无法追溯 | Append-only + 审计测试 |
| **状态机漏洞** | 非法状态迁移（如已退款订单再次发货） | 状态机显式化 + 迁移测试 |
| **额度穿透** | 并发下超额扣款/超卖 | 一致性测试 + 分布式锁 |
| **合规遗漏** | PII 未脱敏、留存超期、跨境违规 | 合规契约逐条对照 |

## 5. 领域覆盖面（按金融系统的四条主线自查）

> **来源说明**：本 skill 的领域视角参考了 `fintech-engineer`（ClawHub 市场，v1.0.3）等公开实践，
> 但已按本 skill 的流程需要**重新组织为自查问题**，未复制其原文表述。
> 金融领域的术语与通用架构模式（KYC、事件溯源、Saga 等）属行业公共知识，不受个别作品专有。

金融系统研发通常横跨四条主线。进入 P2 前，先确认**本次需求涉及哪几条**，
再把涉及的部分展开成具体规格项——**不涉及的直接跳过，别把下面的问题当清单照抄**：

| 主线 | 要回答的问题（展开后转成 P2 规格项） |
|------|--------------------------------------|
| **资金流** | 钱怎么进来、怎么出去、怎么记账？涉及收单 / 出款 / 结算 / 清算 / 对账的哪几段？是否多币种、是否跨境？利息与费用由谁承担、何时计提？ |
| **交易与撮合** | 有没有订单生命周期，状态如何迁移？是否需要撮合，价格如何形成？报价/行情从哪来、延迟容忍多少？持仓与损益按什么口径计算？ |
| **风险与合规** | 适用哪些法规与认证要求？要不要身份核验、名单筛查、可疑上报？敏感数据如何脱敏、留存多久、能否出境？ |
| **技术底座** | 一致性怎么保证（幂等 / 事件溯源 / 补偿事务）？可用性与恢复目标（RTO / RPO）是多少？监控告警覆盖到哪一层？ |

**复杂系统的角色分工建议**（按需，不必齐备）：安全（威胁建模）、基础设施（容量与容灾）、
风控（规则与模型）、数据（存储与治理）、运维（发布与观测）、合规（监管对接）、领域集成（渠道 / 清算 / 链上）。

| 资源 | 查找方式 |
|------|---------|

> ```
> ~/.workbuddy-ai/skills/    ← 本 skill 与通用层（7 个 fstdd-*），
>                              由 install.sh / install.ps1 生成，彼此同级
> ~/.workbuddy/skills/       ← 领域源 fintech-engineer（第三方市场安装）
> ```
>
> 即：**本 skill 与它依赖的通用层在同一目录**（`~/.workbuddy-ai/skills/`），
> 通用阶段 skill 能替它执行流程 —— 不存在"有脑子没腿"。
>
> 唯一跨目录的是**领域源** `fintech-engineer`，它留在 `~/.workbuddy/skills/`
> （第三方市场的安装位置）。这是**设计如此**，不要为"图省事"把它拷到
> `.workbuddy-ai` —— 会造成两份副本，第三方市场更新时两边不同步。

若上表中任一资源找不到，说明 FSTDD 尚未安装 —— 见 Fstdd 仓库 README 的「快速开始」。
