# STDD V3.0 路线图 / Roadmap

> 日期：2026-07-02 · 状态：已确认，推进研发中
> 维护：小以AI实验室
> 基准版本：V2.9.6

## 一、V3.0 目标

STDD V3.0 的核心主题是 **"从代码验证到 Agent 行为验证"** + **"从单项目经验到跨项目知识网络"**。

8 项核心能力：

| # | 能力 | 优先级 | 简要说明 |
|---|------|--------|---------|
| 1 | 知识图谱 `knowledge-graph.yaml` | 🔴 高 | 跨项目失败模式提炼、架构决策模式、修复模板关联 |
| 2 | 跨项目分析 | 🔴 高 | 模式识别、疗效评估、趋势分析、关联发现、风险预测 |
| 3 | (m) Agent 检查点失败 | 🔴 高 | Agent 操作序列 CP 断言验证，操作后世界状态验证 |
| 4 | (n) 跨系统不一致 | 🔴 高 | 多系统间运行时数据值一致性校验 |
| 5 | Human View 完整自动生成 | 🔴 高 | 从 Canonical YAML 渲染完整人类可读文档（全类型覆盖） |
| 6 | Agent 验证管线独立运行 | 🔴 高 | `agent_tests/` 目录 + CP 验证器，Phase 5 双管线并行 |
| 7 | Guard 智能模式（阶段 2） | 🟡 中 | 分级提醒：小改放过+提醒 / 中改放行+建议 / 大改拦截+引导 |
| 8 | Guard 自动启动（阶段 3） | 🟡 中 | 自动创建 lightweight change，无感追踪，事后可追溯 |

## 二、各模块详细设计

### 2.1 知识图谱 `knowledge-graph.yaml`

**数据结构**：`nodes`（失败模式/设计决策/修复模板/语言 idiom）+ `edges`（causes/prevented_by/refines/appears_in）+ `metrics`（出现次数/趋势/修复成功率）

**CLI 命令**：
- `stdd knowledge merge` — 从社区拉取 + 本地合并去重
- `stdd knowledge query <pattern>` — 图谱查询
- `stdd knowledge predict <change>` — 风险预测
- `stdd knowledge fix <EXP-ID>` — 修复建议

**数据流**：项目经验 → Phase 6 DELIVER 上传 → 社区 git 库 → `stdd knowledge merge` 合并图谱 ←→ 本地项目消费

---

### 2.2 跨项目分析

本质是在知识图谱上做查询和统计：

- **模式识别**："这个 bug pattern 之前在哪些项目出现过？"
- **疗效评估**："修复模板 X 的有效率是多少？"
- **趋势分析**："契约断层是越来越多还是越来越少？"
- **关联发现**："哪些失败模式经常一起出现？"
- **风险预测**：基于 change 特征匹配历史相似 change 的失败模式分布

---

### 2.3 (m) Agent 检查点失败

Agent 操作序列中任一 CP 的断言未通过。子类型：

| 子类型 | 现象 | 根因 |
|--------|------|------|
| CP 断言失败 | 操作后环境状态与预期不一致 | Agent 操作了错误的数据或 API |
| CP 执行超时 | Agent 在某步卡住 | 网络/系统不可用或死循环 |
| CP 依赖链断裂 | 上游 CP 失败导致下游全部跳过 | 级联效应（类似 (c) 但作用于操作链） |

**检查时机**：Phase 5，Agent 验证管线独立运行。

---

### 2.4 (n) 跨系统不一致

多系统间运行时数据值不一致。与 (k) 契约断层的区别：

| | (k) 契约断层 | (n) 跨系统不一致 |
|---|---|---|
| 检查对象 | API 字段名/header 命名一致性 | 系统间运行时数据值一致性 |
| 方式 | 静态代码分析 | 运行时查询+比对 |
| 例 | 后端返回 `token_balance`，前端读 `balance` | CRM 余额 8000，财务余额 10000 |

---

### 2.5 Guard 智能模式（阶段 2 + 阶段 3）

**阶段 2 · 提醒模式**：
- 小改动（单文件 <10 行）→ 放行 + 温和提醒
- 中等改动（2-3 文件 <50 行）→ 放行 + 明确建议启动 STDD
- 大改动（>3 文件 或 >50 行 或核心模块）→ 拦截 + 引导 `/stdd-understand`

**阶段 3 · 自动启动**：
- 检测到大规模变更时自动创建 lightweight change
- 触发条件：文件 ≥3 或行数 ≥50、距上次 change >24h、用户未拒绝
- 默认 lightweight 模式（复杂度 ≤3），保留 TDD 底线

## 三、实施计划

V3.0 分 **3 个 Change** 逐步推进：

### Change A：知识图谱 + 跨项目分析

| 条目 | 内容 |
|------|------|
| 新建文件 | `stdd/cli/commands/knowledge.py` |
| 数据模型 | `knowledge-graph.yaml` schema + `.stdd/templates/canonical/knowledge-graph.yaml` |
| CLI 命令 | `stdd knowledge merge/query/predict/fix` |
| 集成点 | Phase 6 DELIVER 自动触发 merge；Phase 2 SPEC 调用 predict |
| 测试 | TC-KNOWLEDGE-001~010 |

### Change B：两种新失败模式 (m)(n) + Agent 验证管线

| 条目 | 内容 |
|------|------|
| 数据模型 | `agent_spec.yaml` 扩展（cross_check 字段） |
| CLI 命令 | `stdd agent verify`（CP 逐条执行 + 跨系统比对） |
| 目录 | `agent_tests/` → CP 验证器测试代码 |
| Phase 5 集成 | 代码验证管线 + Agent 验证管线并行 |
| 经验库 | 新增 `agent_cp_failure`、`cross_system_mismatch` 两个类别 |

### Change C：Guard 智能模式 + Human View 完整生成

| 条目 | 内容 |
|------|------|
| Guard 阶段 2 | 分级提醒逻辑（小/中/大改动判断 + 提醒去重） |
| Guard 阶段 3 | 自动 lightweight change 创建 |
| Human View | `canon generate --all` 覆盖所有文档类型（design/spec/test-plan/slices） |
| 配置 | `.stdd/config.d/guard.yaml`（提醒阈值、排除目录、去重策略） |
