# 一次性生产数据修复 / 迁移作战手册

适用场景：**「某张表有 N 行字段为空」「有 M 行明显不该存在的脏数据」「指标口径要换」**。
特征：一次性执行 + 写生产库 + 之后靠 ETL 常态维护。

不适用：常规增量 ETL 开发、schema 迁移（用 migration 工具）、纯查询分析。

---

## 铁律 0：先找「真源」，再决定改哪里

**任何派生表在被改之前，必须先回答：谁在什么时候用什么方式重建它？**

```bash
# 找出谁在重建这张表
grep -rn "CREATE OR REPLACE TABLE.*<table>\|TRUNCATE.*<table>\|DROP TABLE.*<table>" .
grep -rn "<table>" --include=*.py -l | head
```

三种常见结论：

| 结论 | 含义 | 该改哪里 |
|---|---|---|
| 表由某个文件/上游**全量重建**（`CREATE OR REPLACE ... AS SELECT`） | 表是上游的**纯函数** | **只改上游**；改表会被下次重建无痛回滚 |
| 表由增量 UPSERT 维护 | 表是累积态 | 直接改表 + 补一次上游对齐 |
| 表就是原始表 | 无上游 | 直接改表 |

> ⚠ **绝不要「双写」**（同时改上游和派生表）。那会造出**第二个会漂移的真源**。
> 早前若已有文档写「必须双写」，那多半是没找到真源时的错误结论。

**但**：若上游重建成本很高（跑全量 ETL 数十分钟），仍应为一次性追补保留一条
「直接改派生表」的旁路，并让它在提交后断言与上游一致。

## 铁律 1：缺口统计必须「按处置路径分层」

当一次修复同时包含**字段回填**与**行删除**时，别只统计一个总数。

```
初始 NULL = 可回填 + 落在待删行上的 + 结构性不可回填的
```

必须把每个数字的来源写清楚，并**同时给出中间态与终态两套期望值**：

```yaml
expected_fill: 24642
expected_null_after_fill_only: 90      # 只回填、未清理
expected_null_after: 89                # 回填 + 清理（= 每标的首行）
```

否则测试的预置条件会写错，测试会在**错误的状态**下 PASS。

自检算术：把「初始 → 中间态 → 终态」三段逐项列出来验一遍，不要只验终态。

---

## 铁律 2：删除脏行必须有守卫，且守卫要能拦住「日历自身有误」

**三重守卫**（同时满足才删，否则只告警）：

1. 键不在权威「白名单」里（交易日历 / 有效主数据集合）
2. 键**严格早于**白名单的最大值（**绝不删最新一天** —— 可能是当日尚未入库）
3. 该键的数据满足**强指纹**：位于周末，**或**与上一有效键的对应行逐行完全相同（多字段比对）

第 3 条是关键：只凭「不在日历里」就删，在日历本身落后时会把真实数据删掉。

同时：白名单为空时必须**保护性中止**，且中止路径也不得留下任何写入。

## 铁律 3：口径用**全量厂商对撞**，不用抽样

若目标列在别的数据源里已有值，拿它对撞：

```sql
-- 找「公式偏离」的行，然后问：这些行是否全部落在同一个可疑日期/同一类事件上？
SELECT count(*) FROM t WHERE source='<vendor>'
  AND abs(col - (<formula>)) >= 1e-2;
```

- 100% 吻合 → 公式与口径确认，且「未复权」这类语义由厂商背书，不是自己推的
- 有偏离 → 看偏离是否**全部集中**在某个已知异常日期上（那是数据缺陷，不是公式错）

**「未复权」口径的必然副作用**：除权除息日会出现超限跳变。
这类行要能**被解释**（命中分红表 / 位于序列前 2 行），而不是断言「数量必须等于 N」。

## 铁律 4：计划要对**每个写入目标各自求值**

> ★ 本手册最重要的一条。

当 A 是 B 的纯函数、而脚本要同时改 A 与 B 时：

```
❌ 从 A 推导出计划 plan → 用它改 A，也用它改 B
✅ 对 A 求一次计划（改 A），对 B 再求一次计划（改 B）
```

**为什么**：A 一旦修好，从 A 推导的计划就变空了 → 改 B 时静默什么都没做。

同理，**早退判定**要针对每个目标分别计算「是否还有事可做」，且必须只数
**真正会被改写的行**（例：结构性永久为 NULL 的首行不能计入，否则永不早退）。

## 铁律 5：断言区分「迁移前的期望值」与「迁移后的不变量」

| 类型 | 例子 | 能否作常驻断言 |
|---|---|---|
| 迁移前的期望值 | `待填行数 == 24642`、`max_date == '2026-09-11'` | ❌ 只能作 dry-run 预检 |
| 迁移后的不变量 | `NULL 行数 == 标的数`、`max_date == max(calendar)`、`总数 == 上游总数` | ✅ |

**通用规则**：一次性迁移的验收测试，**必须区分**这两类。
把「迁移前的期望值」写进常驻断言 = 下次跑必红。

另外警惕**两态通吃**的假断言：`len(x) in (0, 81)` 这种「两种状态都接受」的写法，
已经无法区分通过/失败，等于没断言。要么断言终态不变量，要么用确定性 fixture 证明机制。

## 铁律 6：删除与写入必须**对称留痕**

- 上游侧删 N 行 → 落盘一份 N 行 × **全部业务列**的 CSV（不只主键）
- 派生表侧删同样 N 行 → 也要有对应留痕，路径与行数进日志
- 原文件被原地改写 → 改写前 `copy` 一份带时间戳的备份
- 文本/JSON 原地改写 → 用 `tmp + os.replace`（同目录同盘才原子）

**验收**：把备份读回来，核对「修复前的计数」逐项吻合。这本身就是一条测试用例。

---

## 铁律 7：写库失败要回滚，连接生命周期要统一收口

- 多个写语句必须**单事务**；任一失败 `rollback()` 后 `raise`，不留半成品
- `main()` 用 `try/finally` 统一关连接，别在每个 `return` 前手写 `close()`
  （异常路径最容易被漏掉）
- 校验失败要在**所有**分支都以非零码退出，不能只在「写入路径」里退非零

## 铁律 8：`字段 IS NULL 的行数 == 0` **不是**不变量

对「源可能缺失」的字段，NULL 数会随上游采集节奏反复出现，把它写成断言 = 每天假红。

```sql
-- ❌ 错：只在「该字段总该有值」时才成立
SELECT count(*) FROM t WHERE amount IS NULL;

-- ✅ 对：可回填缺口 == 0（源有值而表为 NULL）
SELECT count(*) FROM t k
  JOIN src s ON s.id = k.id
 WHERE k.amount IS NULL AND s.amount IS NOT NULL;
```

**真实案例**：每日 ETL 有一条「直连主站补当日新行」的步骤，该通道**不产出 `amount`**；
而 amount 的唯一来源表当日数据尚未到位 → 每天新增 89 行 `amount IS NULL`。
修复脚本正确地**拒绝编造**并输出「无源」告警，次日源到位后由同一脚本自愈。
若断言 `amount IS NULL == 0`，测试在**上线当天**就变红。

**写断言前先问**：「这个字段**是否总该有值**？」
- 总该有值（如主键、外键、非空业务字段）→ 可以断言 NULL == 0
- 源可能缺失（可选字段、依赖上游通道的字段）→ 只能断言「可回填缺口 == 0」

> 这与铁律 5 同源：铁律 5 讲「别绑死修复前状态」，本条讲「别把**源本身的缺失**误判成**修复失败**」。
> 同一变更里这类断言脆弱点复发率极高（本项目实测 5 次），写断言时应当作 checklist 逐条过。

## 铁律 9：E2E 验证选「覆盖命题真值的最短链路」，不是「跑最多步骤」

**真实案例**：回滚验证选了「完整每日 ETL（10 步）」，第一次跑到第 2 步（网络取数，89 只串行）
**被会话/终端边界杀掉**，留下僵尸锁；改跑与命题相关的 5 步链路，5 分钟完成且结论等价。

做法：
1. 先写清命题 —— 例：「修复不被每日全量重建回滚」。
2. 列出该命题的**唯一写路径** —— 例：`补录 → 修复 → build → 反向同步`。
3. 其余步骤若**对目标表无任何写入路径**，纳入与否不改变命题真值 → 排除，并在报告中显式声明范围偏离。

**两个配套事实**（都要预先知道）：
- 长跑子进程会被会话边界杀掉；因此**运行锁的僵尸自动接管**（`锁时长 + PID 存活探测`）是必要防线，
  下次启动要能自动接管而不是被永久卡死。
- 统一执行器若用 `p.communicate(timeout=...)`，输出是**全缓冲**的 → 长步骤期间日志文件不增长。
  排查「在算 vs 卡死」不能只看日志 mtime，要查**进程存活**（`tasklist /FI "PID eq <pid>"`）
  或该步骤的**副产物 mtime**。

## 铁律 10：新判据 / 新实现必须与**独立参照**逐行对账，再落库

> ★ 与铁律 4 并列，都是「差一点就出生产事故」级别的。

当你要写一个**新的判据或解析实现**（判空规则、口径换算、字段抽取、正则清洗）时：

```
❌ 写完 → 单元用例过 → 直接落库
✅ 写完 → 单元用例过 → 与一份**独立实现**对**全量**逐行对账 → 一致才落库
```

**为什么**：新实现最容易在**边界数据**上静默失效 —— 不报错、不抛异常，
只是把分布算成了另一个样子。而"分布看起来合理"正是最危险的信号。

**真实案例（2026-09-15）**：为某文本表加 `payload_len` / `is_empty` 派生列，
判据是"剥掉样板行/分节标题/框线/占位串后的实质字符数"。

- 分节标题正则写成 `^【[^】]*】[ \t]*$`。
- 该文本行尾是 **CRLF**。Python `re` 的 `$` 在 `MULTILINE` 下**只匹配 `\n` 之前**，
  `\r` 卡在中间 → **整个正则一个都匹配不上**。
- 后果：标题文字 `1.持股明细` 被当成正文计入 payload（28 字符 > 阈值 20），
  于是「持股明细」这一栏从**全空 93/93** 变成**"35 只有数据"**。
- 全局分布从「5 个 tab 全空」变成「3 个 tab 全空」，**看起来完全合理**。

抓出它靠的是**与既有探测脚本逐行对账**：`一致 0 只，不一致 93 只`。
若跳过这步直接落库，错误分布会被固化进生产表并被下游当权威用。

**做法**：
1. 保留一份**独立参照**（旧脚本、朴素写法、第三方实现都行），不要共用正则/常量。
2. 对**全量**逐行比数值，**不看汇总**。汇总会把 93/93 的差异平均掉。
3. 不一致就查到底，**不要假设"新的对、旧的有 bug"** —— 本例中恰恰是新的错。
4. 单元用例要覆盖**三类边界**，缺一不可：
   - 纯占位/纯空（期望 0）
   - 有真实数据（期望正数）
   - **含特殊结构**（如正文里出现与分节标题同形的内容 `【2026-08-31】…公告`）
     这类最容易暴露"正则过宽把正文也删了"。

**衍生规则**：新实现要**收敛成唯一入口**（如 `core/xxx.py`），
旧脚本改为 import 它，消除第二份实现 —— 否则下次阈值一改又漂移。
但**先对账、后收敛**：对账期间两份实现必须保持独立。

## 常见技术坑速查

| 坑 | 症状 | 解法 |
|---|---|---|
| ORM/驱动把 list 参数按元素类型适配 | `操作符不存在: text = record`（元组被当 composite） | 归一成标量列表：`_normalize_dates()`，两种形状都接受 |
| 数据访问层有两个入口、游标类型不同 | `TypeError: tuple indices must be integers` | 按列名取数必须用返回 dict 行的那个入口；在函数 docstring 写死 |
| 日期列类型是 TEXT | `操作符不存在: text >= date` | 显式 `::text` / `::date` 转换，两边对齐 |
| 中文输出乱码 | 打印异常 | `PYTHONIOENCODING=utf-8` |
| 长任务被前台超时打断 | 命令被 kill | 后台跑 + 落日志文件，定期 tail |
| 统一执行器全缓冲输出 | 长步骤期间日志不增长，误判为卡死 | 查进程存活（`tasklist /FI "PID eq <pid>"`）或副产物 mtime，别只看日志 mtime |
| 长跑进程被会话/终端边界杀掉 | 留下僵尸锁，后续运行被挡 | 锁要带「时长 + PID 存活探测」的僵尸自动接管；下一次运行必须能自愈 |
| 正则用 `[ \t]*$` / `\s*$` 匹配行尾 | **CRLF 文本上 `[ \t]*$` 一个都匹配不上**（`$` 只匹配 `\n` 前，`\r` 卡住）；`\s*$` 能匹配但会跨行吃空行 | 行尾用 `[ \t\r]*$`；或用 `re.sub(r"\r\n", "\n", t)` 先归一化行尾再处理 |
| 断言「NULL 数 == 0」 | 上游源缺失时每天假红 | 改断言「可回填缺口 == 0」（见铁律 8） |
| 「源缺失」fixture 用了源表里存在的键 | 经真实入口（会自行加载真实源）时测的变成「源有值」，断言恒假 | fixture 必须用真实源中**确实不存在**的键（假 ID + 远早日期）；反向换回真实键应能变红 |

## 执行编排（建议顺序）

```
0. 只读侦察（多个诊断 SQL，全部只读）
   ├ 缺口分层统计
   ├ 白名单/日历洁净度检查（有无周末行、有无缺真实交易日）
   ├ 口径全量对撞
   └ 上游/派生表逐字段核对（确认是纯函数关系）
1. 写提案：数字锚点 + 目标 + 范围 + 风险 + 决策点
2. 写规格 + 测试方案 → 用户确认（Gate）
3. 先写测试 → 看到预期失败（RED）
4. 实现 → GREEN → 重构
5. **新判据/新实现与独立参照全量逐行对账** ← 见铁律 10
   （跳过这步 = 把可能错误的分布静默固化进生产表）
6. 预演（dry-run）→ 核对计划数与提案逐项吻合
7. 取得明确授权后执行：先上游、再派生表；每步落备份
   - 若本次是「加派生列」：加列本身非破坏性，但全量 UPSERT 会重写整表 →
     **必须额外断言「业务列与备份逐行一致」**，证明只加列、没动正文
8. 断言三系统一致（上游 / 主库 / 只读副本）
9. 跑常规 ETL，证明修复不被重建回滚 ← 最容易漏、也最容易被用户在意
   （优先跑**完整**编排；若长跑步骤被会话/终端边界杀掉，退化为「覆盖命题真值的最短链路」，
     并在报告与调整台账里显式声明范围偏离 —— 见铁律 9）
10. 质量检查：语法 / lint / 调试残留 / 死代码 / 12 类失败模式
11. 沉淀：设计调整 + 经验库 + 测试报告
```

**第 9 步是关键**：只跑「重建那一步」不足以证明安全，跑完整编排才能暴露
「编排顺序错」「新增步被跳过」「副本没传播」这类问题。
**但**：完整编排常含 40 min+ 的网络取数步骤，且会被终端边界杀掉。
先判断「哪些步骤对目标表有写入路径」，再决定范围 —— 无写入路径的步骤不改变命题真值。

## 汇报模板（给用户）

```
终态：<行数> / <各字段 NULL 数> / <脏行数> / <实体数>，三系统一致
写入：<上游> +N 行 / <主库> +N 行 / 删除 M 行（单事务，VERIFY OK）
备份：<路径清单，每个都注明确认过的行数>
执行期抓到的真实缺口：<编号 + 一句话 + 若不发现的后果>
已知问题：<编号 + 原因 + 影响 + 补完计划>
待确认：<下一道门 / 需用户决策的点>
```

**要如实说明「执行期发现并修了什么」** —— 一次性数据修复的真实价值往往在这里，
而不是「填了多少个空」。
